# 05 首次开启对账与作废后的重对账

Status: resolved

「取消：零写请求」「快照确实先落了一份，且用的是固定的 reason」
「基线清空 + 服务端已有非默认目标 → 重新对账不产生冲突」）
Type: task
Part of: `.scratch/sync-client/spec.md`
Blocked by: 04

## 目标

第一次打开开关时是一次明确的对账，而不是静默推送；导入 / 回滚 / 清除数据之后基线作废，
由用户决定何时重对账。

## 改动点

- 首次开启：
  - `health.seq === 0`（服务端空）→ 全量推本地数据。
  - `seq > 0`（服务端已有数据）→ 弹一次确认，三选一：**以本机为准**（全量推，会覆盖服务端）/
    **以服务端为准**（拉 `/v1/snapshot` 覆盖本机，且**先自动留一份本地快照**）/ **取消**
    （开关保持关闭，一个请求都不发）。
  - 取消不视为错误，只是没开。
- 导入 / 回滚 / 清除数据之后：基线作废；**不自动推全量**（那等于拿刚导入的数据去覆盖服务端），
  设置卡显示「需要重新对账」与一个按钮，由用户点。

## 一个必须在这里处理的边界：`dietGoals` 恒有值

工单 04 的集成用例发现的：`dietGoals` 是**模块单值**，而 store 里它**恒有默认值**
（`{calories: 2000, protein: 80}`）。所以在空基线下它**必然产生一条 push**，
哪怕「本机什么都没干」。三种情形后果不同：

| 情形                                       | 后果                                                                                       | 该怎么做 |
| ------------------------------------------ | ------------------------------------------------------------------------------------------ | -------- |
| 首次开启 + 服务端空（`seq === 0`）         | 推上去是对的：服务端本来就该有这份值                                                       | 照常推   |
| 首次开启 + 服务端有数据 + 选「以本机为准」 | 推上去是对的（用户明确选了覆盖）                                                           | 照常推   |
| **基线作废后重新对账**                     | 本机是默认值、服务端已有真实目标 → 推上去会被判 `conflict`，**用户看到一行莫名其妙的冲突** | 见下     |

第三种是真正要处理的：**重新对账的语义是「对齐」而不是「覆盖」**，所以那条路径上应当
先拉 `/v1/snapshot` 看清服务端有什么，再决定推什么；或者对「本机仍是默认值」的单值模块
**跳过推送**（服务端那份更可能是用户真设过的）。

判据：`dietGoals` 的默认值是「用户从没设过」的基准，客户端已有一份同语义的常量
（`DEFAULT_DIET_GOALS`，而且 `schemas-parity.test.ts` 断言服务端那份与它相等）。
**把它写进用例**：基线清空 + 服务端已有一份非默认目标 → 重新对账**不该**产生冲突提示。

## 验收

- `seq === 0` → 全量推；`seq > 0` → 出确认，且选「取消」时**一个写请求都不发**。
- 走一次导入 → 设置卡显示「需要重新对账」，且**没有**自动推送。
- 「以服务端为准」路径里，本机快照确实先落了一份。
