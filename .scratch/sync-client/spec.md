# V2.0 同步客户端接入

Status: needs-triage
Type: spec
来源：`/to-spec`（2026-10-02）。与 `.scratch/sync-service/spec.md` 配对：那份管本机服务端，
这份管浏览器这边怎么推、怎么拉、怎么落库、怎么告诉用户。
关联：`docs/adr/0002-…`；`CONTEXT.md` 的同步 / 令牌 / 设备 / 记录版本 / 墓碑 / 冲突六个词条；
`.scratch/backup-diet-targets/spec.md`（同步的前置：副本必须与备份模块对得上）。

## Problem Statement

服务端那份 spec 把接口、时钟、墓碑、冲突都定死了，但客户端现在**一点同步能力都没有**：
没有设备标识、没有「哪些条目改过」的记录、没有把远端变更写回 store 的入口、没有开关与令牌输入。

难点在于「哪些条目改过」判定不了：这个仓库的 `updatedAt` 只覆盖写作项目、复盘、日记三类记录，
且由各 action 手工维护、多个 `updateX` 直接绕过（ADR-0002 记过）。同步第一版又明确不补这个字段，
所以只能**比对内容**。

## Solution

一个可丢弃的本地基线 + 一个纯编排的同步引擎 + 设置页一张卡。

**改动的判定：内容哈希基线。** 每次同步成功后，把「模块 → 条目 id → 内容哈希」写进
`lm:sync` 的基线表；下次同步对当前数据算同样的哈希再比：

| 基线 | 当前         | 判定 | 动作        |
| ---- | ------------ | ---- | ----------- |
| 无   | 有           | 新增 | 推 `put`    |
| 有   | 有且哈希不同 | 改过 | 推 `put`    |
| 有   | 无           | 删了 | 推 `delete` |
| 有   | 有且哈希相同 | 没动 | 什么都不做  |

- 哈希 = `crypto.subtle.digest('SHA-256', 规范化 JSON)` 取前 16 个十六进制字符。
  「规范化」= 递归按键名排序后再 `JSON.stringify`：`JSON.stringify` 的键序取决于对象构造顺序，
  直接哈希会让同一条记录算出两个值。
- **基线是可丢弃的派生物**：删掉 `lm:sync` 只会让下次同步退化成「全量比对」，
  而且因为「基线里没有的 id 不产生 `delete`」，它不会误删任何东西。

**同步单位：直接复用服务端那份 spec 的表**，落在 `src/services/sync/units.ts` 里，每个单元记三件事：
怎么读（从哪个 store 取）、怎么按 id 写（upsert / delete）、模块名（用备份的模块名）。
表里的「不同步项」（`lm:theme` / `lm:ui`、`focus.active`、`recent*Names`）在这个文件里
以注释形式列出来，写明为什么不同步 —— 免得后来者以为漏了。

**落库方式：`setState` + 按 id 的 upsert/delete 纯函数，不碰 21 个 store 的内部。**

- 理由：远端那份记录是另一台设备写完、而且经过客户端 schema 校验的**整条记录**。
  走各模块自己的 `updateRecord` 会把派生字段按本机逻辑重算一遍，两端反而可能算出不同结果。
- 代价：落库不重跑 store 的业务不变式（例如饮食记录的四个合计数不会重算）。所以要有测试锁住
  「落库后逐字段等于服务端那一份」；记录本身带合计数，正常路径上没有差异。
- 写入走 `useXStore.setState`，zustand 的 persist 中间件照常把结果写进 IndexedDB —— 不需要新入口。

**一轮同步的流程（顺序固定：先推后拉）。**

1. `GET /v1/health`：连不上就到此为止（离线是正常状态，不是错误）。
2. 算 diff → `POST /v1/push`（每条带 `baseRev` 与 `deviceId`）。
3. 记下 `status: 'conflict'` 的条目（进 `lm:sync.conflicts`，只留最近一次）。
4. `GET /v1/changes?since=<lastSeq>` 分页拉完 → 逐条落库（`put` / `delete`）。
5. **全部成功之后**才更新 `lastSeq` 与基线表。

任何一步失败：不改 `lastSeq`、不动基线（已落库的条目保持已落库）—— 幂等，下一轮重来即可。

**触发时机：开机一次 + 手动。** 开机那次接在 `main.tsx` 里 `syncFolderBackup()` 旁边，
同样**动态 import**（同步引擎会拉进 HTTP 与哈希代码，不该进首屏包 —— 首屏预算是 300 KB，
现在用掉 167.3 KB gzip）。设置页给一个「立即同步」。**不做定时轮询**：省电、省网络，
也避免半开的请求拖着界面。

**首次开启（必须是一次明确的对账，不是静默推送）。**

- `health.seq === 0`（服务端空）→ 全量推本地数据。
- `seq > 0`（服务端已有数据）→ 弹一次确认，三选一：
  **以本机为准**（全量推，会覆盖服务端）/ **以服务端为准**（拉 `/v1/snapshot` 覆盖本机，
  且**先自动留一份本地快照**）/ **取消**（开关保持关闭，一个请求都不发）。
- 取消不视为错误，只是没开。

**令牌与设备标识都存在 `lm:sync` 里，绝不进备份、绝不进导出。** 导出文件会落到同步盘、U 盘、
聊天窗口里，令牌跟着走等于把钥匙一起寄出去。这条要有测试盯着（见 Testing Decisions 第 4 条）。
设备标识首次开启时生成一次（复用 `utils/id.ts` 的 `createId`）。

**导入 / 回滚 / 清除数据之后：基线作废。** 这三种操作会让 id 集合与内容大改，此时**不自动推全量**
（那等于拿刚导入的数据去覆盖服务端），而是在设置卡里显示「需要重新对账」和一个按钮，由用户点。

**冲突怎么让用户知道。** `push` 结果里 `conflict` 的条目记进 `lm:sync.conflicts`，
界面上给**一行提示**（可点，进设置卡的明细：模块 + 条目标题 + 服务端那份的时间），
不弹模态、不阻塞。侧栏底部那行保存状态**不改** —— 它只回答「本地写没写成功」
（`store/saveStamp.ts` 的原话），把同步状态塞进去会把两个问题混在一起。

**界面：设置页「数据概览」旁加一张「跨设备同步」卡。** 开关、服务地址、令牌输入（打码、可清除）、
最近一次同步的时间与结果（成功 / 失败原因 / 冲突几条）、「立即同步」与「重新对账」两个按钮，
以及一行说明：**关闭时应用仍是零网络请求**。

## User Stories

1. 作为一个用户，我想在设置页打开一个开关、填一次地址与令牌，就让两台设备对上。
2. 作为一个用户，我想开机后它自己同步一次，不用我每次手动点。
3. 作为一个用户，我想关掉开关后应用完全不联网，这样「默认纯本地」是我能验证的。
4. 作为一个用户，我想在服务没跑、或没网时照常用应用，只是同步那行显示失败。
5. 作为一个用户，我想另一台设备改的东西能落到我这台，包括**删除**。
6. 作为一个用户，我想在两台都改了同一条时事后看到一行提示，而不是静默丢一份。
7. 作为一个用户，我想在第一次打开同步时被明确问一次「哪边为准」，而不是被静默覆盖。
8. 作为一个用户，我想导出的备份里**没有**我的令牌，这样备份文件可以放心放到别处。
9. 作为一个用户，我想导入一份备份之后不被自动推到服务端，这样我不会用一份旧文件覆盖两台设备的数据。
10. 作为一个维护者，我想同步引擎与首屏包无关（不进 300 KB 预算），这样它不会拖慢打开速度。
11. 作为一个维护者，我想同步的写入不经过 21 个 store 的内部改动，这样我不会为了同步去重构数据层。

## Testing Decisions

**什么算好测试。** 只测外部行为与可观察结果：给引擎喂一个假的 HTTP（在 fetch 层打桩），
断言「发出去的载荷是什么」「store 里的数据变成什么」「`lm:sync` 里记了什么」。不测内部函数名、
不测 React 渲染细节（设置卡那层按既有页面测试的写法另加几条）。

1. **diff 三种判定**：新增一条、改一条、删一条 → 推送载荷的 `module` / `key` / `op` / `baseRev` 正确，
   没动的条目一个都不推。
2. **落库**：拉到 `put` 与 `delete` → store 里确实变了，且**只变那一条**（另一条逐字段不变）。
3. **失败不改游标**：第 4 步中途抛错 → `lastSeq` 没前进、基线没更新；立刻重跑一遍不会产生重复条目。
4. **令牌不进备份**：`serializeBackup(readAllData())` 的结果里搜不到令牌字符串，也搜不到 `lm:sync` 的键。
5. **首次开启两个分支**：`seq === 0` → 全量推；`seq > 0` → 出确认，且选「取消」时**一个写请求都不发**。
6. **离线**：`fetch` 直接 reject → 应用照常用、状态显示失败、store 一字未改、`lastSeq` 不动。
7. **冲突留痕**：服务端返回 `conflict` → `lm:sync.conflicts` 里有一条，界面上出现那行提示。
8. **导入后作废**：走一次导入 → 设置卡显示「需要重新对账」，且**没有**自动推送。
9. **基线可丢弃**：删掉 `lm:sync` 后同步仍能跑（退化成全量比对），且**不产生任何 `delete`**。
10. **哈希稳定**：同一条记录用两种键序构造 → 同一个哈希。

**怎么跑。** `npm run test` 全绿（当前基线 1579 条 / 93 文件），新增用例不能靠放宽既有断言通过；
交付前另跑 `npm run typecheck && npm run lint && npm run format:check`。真浏览器冒烟
（`npm run e2e`）**不覆盖同步**：本机服务不进 CI，e2e 里起一个假服务得不偿失。

## Out of Scope

- **服务端本身**：见 `.scratch/sync-service/spec.md`。
- **字段级合并**：ADR 已划到 V2.1，需要真实冲突样本。
- **定时轮询 / 后台同步**：第一版只有开机一次与手动。
- **手机端**：要从局域网连过来，得先解决监听地址与 TLS，连带「家里这台机器必须开着」这条代价。
- **端到端加密 / 传输加密**：第一版只在 `127.0.0.1` 上走明文 HTTP，不出本机。
- **给同步做一套新的 UI 组件**：设置卡用既有的 `Card` / `CardHeader` / `CardBody` 与表单件。
- **把同步状态并进侧栏那行保存状态**：那行只回答「本地写没写成功」。

## Further Notes

**不用做的事（免得白写）。** 命令面板的实体索引 `useEntityIndex` 是 `useMemo` 订阅各 store、
且只在面板打开时挂载，远端写入落进 store 之后它自己会失效重算 —— **不需要任何缓存失效逻辑**。
同理，各页列表都是订阅 store 的，落库即刷新。

**与「备份到文件夹」的关系。** `folderSync` 与同步是两条互不相干的通道，都读 `readAllData()`：
一条把整库写进用户授权的目录，一条与服务端逐条对账。两条都开着不冲突，
但**同步的元数据（`lm:sync`）不参与 `readAllData()`**，所以既不会被写进那个目录的备份，
也不会被同步到另一台设备。

**术语别混。** 「记录版本（rev）」是服务端给的、判谁赢的；`lastSeq` 是本机记的「拉到哪了」；
`STORE_VERSION` 是客户端持久化结构版本；`BACKUP_SCHEMA_VERSION` 是备份与副本的结构版本。
写测试名与提交信息时不要用「版本」单独指代前两者。
