# 05 墓碑生命周期与休眠设备

Status: ready-for-agent
Type: task
Part of: `.scratch/sync-service/spec.md`
Blocked by: 04

## 目标

让「删除」能可靠地传给第二台设备，同时不给墓碑无限期占用空间：所有已注册设备都拉过就清，
或超 90 天也清；休眠太久的设备回来时改走全量对账。

## 改动点

- 整条记录被删 → 记墓碑 `{ module, key, rev, deletedAt }`，`op: 'delete'` 按 rev 参与 LWW
  （晚到的写能复活它，这是 LWW 的固有语义，不是 bug）。
- 清理条件（取先到者）：所有已注册设备都拉过 ≥ 该墓碑的 seq；或超过 90 天。
- 清理时把 `purgedThroughSeq` 推到这批墓碑里最大的 `seq`（单调不减）；
  `since < purgedThroughSeq` 的拉取**一律不给增量**，返回与休眠设备同一个「需要全量对账」信号。
- 设备表 `lastSeenAt` 超 90 天的设备再次出现 → 不做增量，返回「需要全量对账」的信号
  （客户端去拉 `/v1/snapshot`）。
- **打卡不产生墓碑**：习惯打卡是记录内部的 `日期 → 数值` 映射（`habitLogs`），删除只是该记录的
  一次普通字段变更；饮水打卡（`dietWater`）同理，只是它按日期键单独成单元。

## 验收

- A 删、B 拉 → B 收到 `delete`；所有设备 ack 后墓碑被清。
- **墓碑清理后，落入 `seq` 空洞的增量拉取必须失败可见、而不是静默返回空。**
  构造一台 `lastSeq` 落在水位之前的设备 → 服务端**拒绝给增量**并要求全量对账。
  （原验收写的「不会把它当成新增」是**恒真**的：记录已删、墓碑已清，服务端对谁都返回空，
  它检测不到真实失效路径 —— 设备本地还留着旧副本、而服务端已无墓碑可告知删除。）
- 90 天未见的设备回来 → 服务端要求全量对账，不给增量。
- 取消一次习惯打卡 → 只产生该习惯记录的一次 `put`，不产生任何墓碑。

## 墓碑清理后的 `since` 空洞（已定案：保留 `seq` 水位）

「所有已注册设备都拉过 ≥ 该墓碑的 seq」与「超过 90 天」两个守卫**都盖不住**下面这条路径：

> 一台设备**仍注册着、仍活跃**，只是它的 `lastSeq` 落后于清理点。它来拉 `?since=<旧值>`，
> 而那段 `seq` 区间里的墓碑已经被清掉了。

两个守卫都放它过去：前者要求「所有设备都拉过」（它没拉过），后者与设备状态无关
（它 89 天没同步也照样落在窗口里）。于是它既收不到 `delete`、也不会被要求全量对账，
**本地的旧副本永远留着**。

**定案（2026-10-02）：取 (a)，保留 `seq` 水位。** 规则：

1. 清墓碑时，把 `purgedThroughSeq` 推到这批墓碑里**最大的那个 `seq`**；该值单调不减，
   与 `seq` 同级放在副本的 `sync` 段里。
2. `GET /v1/changes`：`since < purgedThroughSeq` → **不返回任何增量**，返回与休眠设备
   同一条「需要全量对账」信号（客户端去拉 `/v1/snapshot`）。`since ≥ purgedThroughSeq`
   才是正常增量。`since` 缺失或不合法 → 同样走全量对账，别去猜。
3. 全量对账走完，客户端把 `lastSeq` 置为服务端当前 `seq`，水位这条分支就不再触发。

为什么不取 (b)：墓碑只标记 `purged` 之后，要么**照样不再返回**（空洞原样存在，等于没解决），
要么**永远返回**（那就等于永不删除 —— 一台卖掉的设备会把墓碑无限期钉在文件里）。
一个整数换来「空间有界 + 语义自洽 + 复用客户端已有的全量对账分支」，比在两条糊掉的路径里选一条好。

补充：`since` 由客户端给，服务端不能假设它可信 —— 水位这条规则同时也是对乱传 `since` 的兜底。
推的方向不受影响：设备本地留着旧记录再来推时，`baseRev` 小于服务端当前 rev，走既有的 LWW 冲突路径。
