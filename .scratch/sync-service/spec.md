## Problem Statement

ADR-0002 拍板了「同步服务跑在本机、纯本地降为默认」，但只到取舍层。它没说这个进程存什么、
按什么接口说话、冲突怎么判、删除怎么传、坏了怎么回滚。这些不定死，客户端就没法开工 ——
「按条目 last-write-wins + 删除留墓碑」这条决策本身要三个前置定义才有意义：
**谁是时钟、一条改动的最小单位是什么、墓碑什么时候可以清掉**。

现状里没有任何同步元数据：`tombstone` / `deviceId` / `deletedAt` 在 `src/` 下零匹配；
`updatedAt` 只存在于写作项目、复盘、日记三类记录，且由各 action 手工维护、多个 `updateX`
直接绕过（ADR-0002 已记）。所以服务端不能指望客户端提供时间戳或版本：**时钟必须在服务端**。

## Solution

一个**零依赖的本机 Node 进程**。只服务单用户的多台设备；默认只听 `127.0.0.1`；用一枚预共享
令牌鉴权；数据落在本机磁盘上的一个副本文件里。客户端主写本地、服务端是中转与落脚点：
离线照常可用，联网时把本地改动推上去、把别处的改动拉下来。

**运行形态与依赖。**

- 源码放 `src/server/`，用 `node src/server/main.ts` 直接启动（Node ≥ 24 的类型擦除，实测本机
  v24.19.0 可跑，相对 import 要带 `.ts` 后缀，`allowImportingTsExtensions` 已开）。
- **零新依赖**：只用 `node:http` / `node:fs` / `node:crypto` / `node:path`。与 `e2e/run.mjs`
  同一套取向 —— 能用手写的一百来行解决，就不拉一棵依赖树。
- 放 `src/server/` 而不是 `server/`：这样 `tsc -b`、`eslint .`、vitest 的 `src/**` 三处配置
  一行都不用改。浏览器包不受影响 —— Vite 只打包入口可达的模块，没人 import 服务端。
- 服务端测试标 `// @vitest-environment node`，放 `src/server/*.test.ts`；`npm run test`
  仍然一条命令跑完前后端。

**服务端不校验业务字段。** 只做结构守卫：模块名在册、`id` 是非空字符串、记录是对象、
其余字段原样存。理由：zod schema 住在 `src/services/schemas.ts`，是客户端的资产；让本机服务
去 import 它，等于把服务端绑死在客户端构建链上（zod + 一串客户端 utils），与「独立进程、
零依赖」相冲，而服务端拿到坏数据也没有能力做用户可读的修复。代价：坏记录能进副本 ——
兜底是「客户端推之前先过自己的 schema」+ 服务端保留历史版本与每日快照（见下）。

**数据模型。**

- **副本文件**（`replica.json`）：形状沿用备份信封，`data` 用备份的模块名，
  另加一个 `sync` 段放同步元数据（`seq` / `purgedThroughSeq` / `tombstones` / `devices` / `rev` 表）。
  `data` 段的键 = `BACKUP_MODULES`（23 条），一个不多一个不少 —— **`settings` 不在其中**
  （定案见下）。多出来的 `sync` 键会被客户端导入路径忽略，所以副本文件**可以当备份导入**；
  但它不是逐字段完整的备份（少了 `settings` 那几项外观偏好）。
- **记录版本（rev）**：每条记录一个单调整数，**只在服务端赋值**，客户端时钟永远不参与比较。
- **全局序号（seq）**：每次接受一次写入 +1，是增量拉取的游标。rev 管「谁赢」，seq 管「拉到哪」。
- **墓碑**：整条记录被删时留 `{module, key, rev, deletedAt}`，让删除能传给第二台设备。
- **设备表**：`{deviceId, label, lastSeenAt, lastSeq}`，只用于「哪台设备多久没同步」与墓碑清理。
- **清理水位（`purgedThroughSeq`）**：墓碑被物理清掉到哪个 `seq`，单调不减。
  落后于它的拉取一律要求全量对账（见「删除与墓碑的生命周期」）。
- **变更日志（`sync.changes`）**：每接受一条改动（`applied` / `conflict`）就追加一条
  `{ seq, module, key, rev, op, record? }`，按 `seq` 升序。**`/v1/changes` 就是读它** ——
  工单 04 落地时补上，之前这里没列它，等于「按 seq 返回增量」但没说那些变更存在哪。

  **放在 `sync` 段里，不另开文件**：这样一次原子写就覆盖了全部状态，不必为「副本与日志两个文件
  之间的崩溃一致性」操心，评审时也能一眼看到状态全貌。

  **裁剪（工单 05 做，与清墓碑同一动作）**：丢掉 `seq <= purgedThroughSeq` 的条目。
  水位以下本来就不会再被谁消费 —— `since` 落后于水位的设备一律被要求全量对账（见上），
  所以那些条目留着只是无界增长。墓碑有清理守卫、日志也必须有一条，否则副本文件会一直涨。
  两次裁剪之间日志会增长，上限是「自上次清理以来的变更数」，不是无界。

**定案：`settings` 键不进副本（2026-10-02，选 (b)）。**

`readAllData()`（`src/services/appData.ts:53-59`）产出的 `settings`
（`themeMode` / `appearance` / `accent` / `density` / `sidebarCollapsed`）是 `BackupData` 的一个键
（`schemas.ts:611`，`settingsSchema.optional()`），但**不在 `BACKUP_MODULES` 里**（`:616`，23 条），
上表也没有它的行。那不是遗漏，是定案 —— 三条理由，按分量排：

1. **它是每台设备各自的 UI 状态**（密度、侧栏折叠、皮肤、主题色、明暗）。三台设备有三套合理值，
   副本只有一份：装谁的都是随机的，恢复时就是拿一台设备的偏好盖掉另一台的。与上表 `lm:theme` /
   `lm:ui` 标「不同步」同一条理由 —— 本文「本文拍死的三处」也写明「各设备各保持自己那套」。
2. **选 (a) 要凭空发明一条写入路径**：`settings` 不是同步单元，就没有任何时机把它写进副本。
   要么让客户端在首次全量推送时捎带（＝用后门把它同步了），要么为它加一个「只写不读」的特殊通道。
   两者都是「多一份没人读的数据」，正是本仓库最该避免的那种东西。
3. 代价可控且**不新**：缺 `settings` 的备份是既有路径 —— `parseBackup` 只 `safeParse(source.settings)`
   （`backup.ts:211-215`），失败/缺失就当作「这个模块不在文件里」，导入时保持本机、静默、不告警。

随之修订两处自述：

- 「副本文件同时是一份合法备份」→ **副本的 `data` 段是 `BACKUP_MODULES`（23 条）的完整镜像**，
  可以直接当备份导入（全量对账、灾难恢复都走这条路）；`settings` 不在其中，所以它**不是逐字段
  完整**的备份 —— 换机恢复外观偏好只有「手动导出的备份」这一条路。
- 「副本的 `data` 段必须与备份模块一一对应」→ 收紧为**严格一一对应**：`data` 段的键 =
  `BACKUP_MODULES`，一个不多、一个不少，没有例外行。

**实现约束（这条最容易漏）**：客户端推的载荷里**不含 `settings`**，服务端的结构守卫里它不在册 ——
收到就按「模块名不在册」拒绝。不写死这条，第一次全量推送会悄悄把发起端的 UI 偏好塞进副本。

**两个 keyed 模块在副本里的形状（2026-10-03 定案）。**

上表定死了这两个模块的 **key**（饮水是日期串、目标是模块名），但没说**存进 `data` 段的形状**。
在此补齐，并且是**按客户端形状存**：

```
data.dietWater = { '2026-10-02': { glasses: 8 }, … }      // 日期 → 杯数
data.dietGoals = { calories: 2100, protein: 120 }          // 模块单值
```

理由：`data` 段要保持**与客户端备份同形**，这样副本能直接当备份导入、`/v1/snapshot` 的响应能直接
落库、工单 07 的 mirror 文件（用户拿它当应急备份）也能直接用。若存成「带 key 的单元数组」，
上面每一处消费方都得记得还原一次形状，**漏一处就是又一次「静默变空」**。

身份信息由 `sync.rev` 的 key 承载（`dietWater:2026-10-02`），不需要塞进值里 —— 所以不存在
「值里没有身份就读不回来」的问题。

这条是**可执行的**：`src/server/schemas-parity.test.ts` 用客户端的 `backupDataSchema`
直接校验「空副本」与「带数据的副本」，形状一旦偏离就红灯（实测把单元数组喂给它会被拒）。
服务端另保留对旧单元数组形状的读入兼容（直连过旧版本服务端的副本会带那种形状），
读到就摊回客户端形状并告警。

**协议（四个接口，全部 `Authorization: Bearer <令牌>`，`/v1/health` 除外）。**

| 方法 | 路径                                | 语义                                                                                                                                     |
| ---- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| GET  | `/v1/health`                        | `{ ok, seq, schemaVersion, modules }`，给探针与设置页「连得上吗」用                                                                      |
| GET  | `/v1/changes?since=<seq>&limit=<n>` | 增量拉取：返回 `seq` 大于游标的变更（含墓碑），带 `more` 表示还有；`since` 落在 `purgedThroughSeq` 之前 → 不给增量，返回「需要全量对账」 |
| POST | `/v1/push`                          | 推本地改动：`{ deviceId, baseSeq, changes: [{module, key, baseRev, op, record?}] }`，逐条返回 `applied` / `noop` / `conflict`            |
| GET  | `/v1/snapshot`                      | 整份副本（换机首同步、休眠太久、或 `since` 落后于水位时的全量对账）                                                                      |

**幂等**是硬要求：`op: 'put'` 且内容与现存记录完全一致时返回 `noop`，**不产生新 rev、不写历史**。
客户端第一版靠「内容哈希基线」找改动（没有 `updatedAt` 可用），重推是常态，不是异常。

**冲突：按条目 LWW，服务端定序。** 客户端带 `baseRev`；若它小于服务端当前 rev，
服务端**仍然接受**本次写入（它拿到更大的新 rev，即「后到者赢」），但在结果里标 `conflict`
并把被覆盖的那一份写进历史。客户端收到 `conflict` 时给一行提示，不阻塞、不弹确认框。

这条「总是接受」之所以不会酿成灾难，前提是**客户端只推自己改过的条目**（基线哈希差集），
不推全量 —— 一台离线一个月的设备回来时，动的是它真改过的那几十条，而不是把整库按旧值盖章。

**删除与墓碑的生命周期。**

- 整条记录被删 → 服务端记墓碑，`op: 'delete'` 按 rev 参与 LWW（晚到的写能「复活」它，
  这是 LWW 的固有语义，不是 bug；要防的是「A 删了、B 的旧副本又推回来」——那靠上面的差集避免）。
- 墓碑何时能清：**所有已注册设备都拉过 ≥ 该墓碑的 seq**，或**超过 90 天**，两者取先到者。
- **清理之后怎么不骗人（定案：保留 `seq` 水位）。** 每清一批墓碑，就把 `purgedThroughSeq`
  推到这批墓碑里最大的那个 `seq`（单调不减）。此后任何 `since < purgedThroughSeq` 的拉取
  **一律不返回增量**，改返回与休眠设备同一个「需要全量对账」信号（客户端去拉 `/v1/snapshot`）。
  理由：两个清理守卫都盖不住「设备仍注册、`lastSeq` 却落在清理点之前」这条路径（它本地还留着
  旧副本，而服务端已无墓碑可告知删除）；补一个整数水位比让墓碑永不删除更省事，也比「只标记不
  物理删」更清楚 —— 后者要么照样不再返回（空洞原样存在），要么永远返回（等于永不删除）。
  细节与验收见 `issues/05-tombstones-and-dormant-devices.md`。
- 兜底：设备表里 `lastSeenAt` 超过 90 天的设备再次出现时，**不做增量**，直接要求全量对账
  （拉 `/v1/snapshot`，以服务端为准合并一次），否则它会把早已删掉的记录复活。
- **打卡不需要墓碑**：习惯的打卡日志是记录内部的一个 `日期 → 数值` 映射
  （`src/services/schemas.ts:435` 的 `habitLogs`，**它是模块内私有的 zod schema、没有 export**；
  `habitStore.toggleHabitLog` 就是删掉映射里的一个键），
  删除它只是该习惯记录的一次普通字段变更，随按条目 LWW 一起传播。饮水打卡（`diet.water`）
  同理，只是它按日期键单独成单元。**墓碑只服务于「整条记录」的删除。**

**第二份存储（ADR-0002 的那条代价）。**

- 配置项 `mirrorDir`：服务端每隔 5 分钟与每次写入后（去抖 30 秒）把副本写到该目录下的
  `life-manager-server-replica.json`。文件名与客户端 `folderSync` 的
  `life-manager-auto-backup.json` 分开，同目录互不覆盖。
- 启动时校验：`mirrorDir` 与数据目录**不在同一卷**，否则明确告警（同卷等于第二份与第一份同生共死，
  这条代价就白付了）。
- 写失败不改变同步行为，只记日志并计入 `/v1/health`（副本写不进去是 ADR 的回滚信号之一）。

**自带备份与回滚（ADR 要求「不能只依赖客户端的自动快照」）。**

- `backups/`：每日一份副本快照，保留 10 份（与客户端 `MAX_AUTO_BACKUPS` 同量级）。
- `history.jsonl`：被 LWW 覆盖或被删除的旧版本，保留 30 天，用于「同步把数据改坏了」时人工取回。
- `POST /v1/restore`：从 `backups/` 或 `history` 取回指定版本，要求令牌 +
  `{ confirm: 'restore', source: 'backup' | 'history', ref }`（`ref` 是备份文件名或历史条目 id；
  `confirm` 必须逐字等于 `'restore'`，否则 400 —— 这是防手滑，不是鉴权）。
  **恢复不倒退 `seq`、不改已有 rev**：把那一版的数据当作**一次新的写入集**写回（每条记录拿新 rev、
  分配新 seq），于是所有在线设备的增量拉取自然收敛到恢复后的状态，不需要任何「游标失效」的额外
  约定，`purgedThroughSeq` 也不受影响。代价是恢复自身也会在 `history` 里留痕，这是想要的。
- 原子写：临时文件 + `fsync` + `rename`。启动时发现半写文件就用最近一份好备份顶上并告警。

**版本兼容。**

- 副本与信封都带 `schemaVersion`（当前 `BACKUP_SCHEMA_VERSION` = 20）。客户端声明高于服务端
  支持值 → 拒绝写入并返回明确错误（要求先升级服务端）；低于 → 接受，缺字段由客户端导入路径的
  归一化层补齐（与备份导入同一套）。
- `STORE_VERSION`（12）与同步无关，服务端不认识它，也不要出现在副本里。

**暴露面与鉴权。**

- 默认 `127.0.0.1`，不监听 `0.0.0.0`；放开需要显式配置并在启动日志里重复提醒。
- 令牌：首次启动用 `crypto.randomBytes(32)` 生成，写进 `config.json` 并在控制台打印一次。
- CORS：默认只放行 `http://localhost:*` 与 `http://127.0.0.1:*`（应用可能跑在 5173、4173 或
  其它端口），其它 origin 需在配置里显式加入。

**可观测与运维。**

- 每次同步记一行：设备、推/拉条数、冲突数、耗时。错误单独记，不吞。
- `/v1/health` 兼作探针；设置页用它显示「服务在不在、上次同步什么时候」。
- 自启：提供 `install-autostart.ps1`（写 Windows 计划任务，含崩溃后重启策略）与一个 `.bat` 入口。
- 「线上运行补不全」这条代价要在 `启动说明.md` 里写清：断电 / Windows 重启会同时打掉服务与
  正在用的客户端。

## 前置依赖（2026-10-02 已清）

**副本的 `data` 段必须与备份模块一一对应**，否则「副本同时是一份合法备份」这条性质不成立。
原先有两处对不上，已由 `.scratch/backup-diet-targets` 补齐（实现 `4aa45da`）——
`BACKUP_MODULES` 现为 23 条、`BACKUP_SCHEMA_VERSION` 20。留在这里是为了说明它是怎么被发现的：

- `dietStore.goals`（每日热量 / 蛋白目标）与 `dietStore.water`（饮水打卡）持久化在 `lm:diet` 里，
  但**不在 `BackupData` 里** —— `readAllData()` 没读它们，导入路径也不回写（`water` 全仓只出现在
  `dietStore.ts` 与 `DietPage.tsx`）。这是备份本身的缺口：导出再导入会丢这两样，与「不丢数据」
  的硬约束不符，同步只是让它更显眼。
- 补齐方式与 ADR-0002 的元数据原则一致：给 `BackupData` 加两个模块（`BACKUP_SCHEMA_VERSION` → 20），
  旧备份按缺失处理、不覆盖现有值 —— **不要**靠 `STORE_VERSION`。

## User Stories

1. 作为一个有两台设备的用户，我想在其中一台改完数据后另一台能拿到，这样我不用手动导出导入。
2. 作为一个用户，我想在没开服务、或断网时照常用应用，这样同步不会变成新的单点。
3. 作为一个用户，我想默认不连任何外部服务，只有我打开开关才走本机服务，这样「默认纯本地」是真的。
4. 作为一个用户，我想在服务没跑时看到一句能懂的话，而不是一个转圈或一个报错栈。
5. 作为一个用户，我想知道「这台设备多久没同步了」，这样我能判断数据是不是落后了。
6. 作为一个用户，我想在两台设备改了同一条时不会静默丢整条，而是事后能看到一行提示。
7. 作为一个用户，我想删掉的记录不会从另一台设备复活，这样删除是可信的。
8. 作为一个用户，我想在同步把数据改坏时能把服务端的那一份取回来，这样我不必求助于手工改文件。
9. 作为一个用户，我想第二份副本写在我指定的同步盘目录里，这样这台机器整个挂掉时数据还在。
10. 作为一个维护者，我想服务端零新依赖、能被现有 `typecheck / lint / test` 覆盖，这样它不会
    变成一个我没在维护的影子工程。
11. 作为一个维护者，我想客户端服务端各只有一个真相源（客户端管 schema、服务端管时钟），
    这样两边不会各自漂移出一套语义。
12. 作为一个维护者，我想冲突、墓碑、幂等这三件事有测试守着，这样这套语义不会在后续改动里悄悄变。

## Testing Decisions

**什么算好测试。** 只测外部行为：发一个 HTTP 请求、看响应与磁盘上的副本文件变成了什么。
不测内部函数名、不测模块私有状态、不为「有没有调用某个 helper」写断言。服务端测试全部
`// @vitest-environment node`，用真的 `node:http` 监听 `127.0.0.1:0`（随机端口）与
`os.tmpdir()` 下的临时目录，不起浏览器、不碰 jsdom。

**要测的（按重要性）。**

1. **幂等**：同 `baseRev` + 同内容连续推两次，第二次返回 `noop`，`seq` 不变、历史不增。
2. **LWW 定序**：两台设备先后推同一条 → 后到的 rev 更大、内容后到者的；先到的那份进历史。
3. **增量拉取**：`since=<seq>` 不漏不重；跨越多次推送后连续拉到所有变更。
4. **墓碑传播与 `seq` 空洞**：A 删、B 拉 → B 收到 `delete`；墓碑在所有设备 ack 后被清掉、
   `purgedThroughSeq` 前移；此后一台 `lastSeq` 落在水位之前的设备来拉 → **被要求全量对账**，
   而不是拿到一个「空增量」。（原写法「不会把它当成新增」是恒真的：记录已删、墓碑已清，
   服务端对谁都返回空，测不到真实失效路径。）
5. **休眠设备的兜底**：设备表里 `lastSeenAt` 超 90 天的设备再来时被要求全量对账，而不是给增量。
6. **鉴权**：缺令牌 / 错令牌 → 401，且不写任何数据；`/v1/health` 不需要令牌。
7. **版本兼容**：客户端声明 `schemaVersion` 高于服务端 → 拒绝写入，副本文件保持原样（逐字节）。
8. **原子写**：写入中途被打断（注入一个在 `rename` 前抛错的 fs 适配器）后，副本仍是上一个好版本。
9. **同卷告警**：`mirrorDir` 与数据目录同卷时启动日志里出现告警（用一个可注入的卷判断函数测）。
10. **恢复**：`/v1/restore` 能把 `history` 里的旧版本写回，且此前那份副本进 `backups/`。

**怎么跑。** `npm run test` 全绿（当前基线 1595 条 / 94 文件），新增用例不能靠放宽既有断言通过；
交付前另跑 `npm run typecheck && npm run lint && npm run format:check`。真浏览器冒烟
（`npm run e2e`）本次不覆盖服务端 —— 服务端没有界面，e2e 的价值在客户端接入那一轮。

## Out of Scope

- **客户端接入**：改动的脏检测 / 内容哈希基线表、设置页的开关与令牌输入、冲突提示文案、
  首次开启时的一次全量对账。这些另立一份 spec，服务端只保证接口够它用。
- **字段级合并**：ADR 已把它划到 V2.1，需要真实冲突样本才定得对。
- **CRDT、服务端时钟之外的任何时钟**（客户端时间戳、逻辑时钟）。
- **账号体系、多用户、分享、协作**（ADR 已划红线）。
- **手机经局域网的访问与 TLS**：第一版只服务本机；要让手机连，得先解决监听地址、证书与
  「家里这台机器必须开着」这条固有代价。
- **复用客户端 `folderSync` 的目录句柄**：ADR-0002 已否决（FSA 句柄给不了独立进程）。
- **服务端的界面 / 仪表盘**：它只有日志、`/v1/health` 与一个 `.bat`。

## Further Notes

**四个计数器别混。** `BACKUP_SCHEMA_VERSION`（20，备份与副本的结构版本）、`STORE_VERSION`
（12，客户端持久化结构，服务端不认识）、**记录版本 rev**（每条记录，服务端赋值，判谁赢）、
**全局 seq**（增量拉取游标）。前两个是「结构」，后两个是「次序」。

**与导入的三种策略是两套语义。** `merge` / `overwrite` / `append`（`src/services/backup.ts`）
服务于「拿一个文件覆盖或合并本机数据」，其中 `merge` 纯按 id 存在性跳过、从不比较时间或内容。
服务端不做这三种策略里的任何一种：它的合并单位是单条记录 + rev，且永远先推后拉。

**本文拍死的三处**（都是低成本、可随时推翻的）：

- 打卡 / 饮水这类「日期键 → 数值」的内嵌映射按本文不产生墓碑。`CONTEXT.md`「打卡」与 ADR-0002
  「数据安全」原先写的「取消打卡改为留墓碑」已按事实更正 —— 只有当日期键被拆成独立同步单位时
  才需要墓碑。
- 外观与密度（`lm:theme` / `lm:ui`）**不同步**，只随备份走；连副本也不装它（见「同步单位」表后
  的定案）。若希望多设备统一外观，那是另一条需求，别顺手塞进同步。
- `mirrorDir` 的周期与保留份数（5 分钟 / 10 份 / 30 天历史）是本文拍的，改动成本很低，
  有意见现在提。
