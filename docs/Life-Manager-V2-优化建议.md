# Life Manager V2 优化建议

> 来源：GitHub 同类项目调研（2026-09-29）+ `E:\MyApp` 源码逐文件走查
> 现状基线：10 个功能模块 + 统计页、约 7900 行页面代码、404 个单测全绿、`STORE_VERSION = 11`
> 本文档定位：给 V2 定方向、排优先级、划边界。它不是"功能清单"，是"取舍清单"。

---

## 0. 结论先行

V1 的**地基**已经超出个人项目的平均水准：语义化设计令牌 + WCAG 对比度测试、20+ 个带完整状态的 UI 组件、zod 校验 + 三种合并策略的导入导出、`lm:` 前缀隔离的存储键、路由分包、无障碍专项、404 个单测。**这些不要推翻。**

但走查完各模块页之后，问题也很清楚：它现在更像**"9 个互不相通的记录表单"**，而不是一个每天愿意打开的个人系统。三个洞：

1. **录入摩擦**：每个模块都要"点新建 → 弹窗 → 填 5 个以上字段 → 保存"。个人工具的第一杀手就是录入成本。
2. **模块孤岛**：没有标签、没有跨模块搜索、没有关联。`CommandPalette` 目前只做"跳转 + 切换外观"，`fuzzyFilter` 只用在这里。
3. **数据托底不足**：全部数据在 localStorage（约 5MB 上限），9 个 `persist()` 都没配 `onError`，写入超限不会提示；没有 PWA（`public/` 是空的，`index.html` 无 manifest / service worker），清一次浏览器数据就全丢。

另外，V1 强在**记录**，弱在**计划**与**复盘**：没有时间盒、没有专注计时、没有每日/每周复盘、没有目标。而这恰恰是同类产品留住用户的环节。

### 如果只做 5 件事（按性价比排序）

| #   | 事情                                                                                                                   | 为什么排前面                                                                                             | 规模 |
| --- | ---------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ---- |
| 1   | **命令面板升级成"万能操作台"**：⌘K 既能搜到实体（任务/书/项目/笔记），也能直接执行动作（新建任务、记一笔训练、写备忘） | 一个组件解决所有模块的录入摩擦，改动集中、收益全局                                                       | 中   |
| 2   | **数据层加固**：IndexedDB + 自动快照 + 配额预警 + PWA 可安装                                                           | 现在"清缓存 = 全丢"，对天天用的工具是致命风险                                                            | 中   |
| 3   | **首页改成可配置仪表盘 + 今日时间轴**                                                                                  | 首页决定"这工具是不是我的主场"，现在它只是个导航页                                                       | 中   |
| 4   | **统一标签 + 跨模块全局搜索**                                                                                          | 打破孤岛，让 9 个模块成为一个整体                                                                        | 中大 |
| 5   | **习惯打卡模块 + 体重/围度**                                                                                           | 习惯是回访率最高的功能；体重是健身模块现在**承诺了却没做**的事（`navItems.ts` 写着"训练记录与身体指标"） | 小中 |

### 1.1 具体可抄的点

- **super-productivity**：任务可以"拖到时间轴"成时间盒；有专注计时器和休息提醒；一天结束自动生成"今天做了什么"。→ 对应 F3、F7。
- **uhabits**：习惯不是"连续 N 天"，而是**强度分数**（近期完成率加权），断一天不会归零。→ 对应 F4，比"连续打卡"更抗挫。
- **wger / Ryot**：都靠"**种子数据库**"解决冷启动——动作库、食物库、媒体条目库。手填一切是 V1 最大的录入成本来源。→ 对应 F9、F10。
- **life-os**："解析失败就把原文存下来并标记待整理，输入永不丢失"。这个降级思路可以用在本地规则解析的快录上。→ 对应 F1。
- **dashy**：首页 widget 可增删、可调尺寸、可分组。→ 对应 U1。
- **beaverhabits**：打卡不需要弹窗——点格子即可切换，这是"日更类"功能的标准交互。→ 对应 U4。

### 1.2 明确不要抄的

- **不要抄 Habitica / HabitTrove 那类游戏化**（金币、宠物、排行榜）：单人自用工具里，游戏化很快会变成负担。
- **不要抄 Life OS 的 AI Chat**：需要联网、需要 Key、效果不稳定，与"纯本地"约束冲突。
- **不要抄 dashy 的完整复杂度**（widget 配置中心、多主题包）：我们只需要"一个能调的首页"。

## 2. 现状诊断

### 2.1 已经做扎实的（V2 不要推翻）

| 方面     | 证据                                                                                                          |
| -------- | ------------------------------------------------------------------------------------------------------------- |
| 设计令牌 | `src/styles/tokens.css` 定义全部语义色，`tokens.test.ts` 按 WCAG 逐对核验对比度                               |
| 组件库   | `src/components/ui/` 导出 20+ 组件，含五态、焦点环、`motion-reduce:animate-none`                              |
| 数据安全 | `src/services/backup.ts` + `schemas.ts`：zod 校验、逐条降级解析、三种导入策略、去重、`lm:` 前缀隔离、快照回滚 |
| 迁移     | `src/store/persist.ts` + `STORE_VERSION = 11`，每步变更都有注释记账                                           |
| 工程     | 路由分包 + 骨架屏、ErrorBoundary、a11y 专项、ESLint + Prettier、404 单测 / 32 文件                            |

### 2.2 四个核心短板（附证据）

**短板一：录入摩擦高**
每个模块都是"Card 列表 + Modal/Drawer 表单"，表单动辄 5+ 字段（如 `src/pages/FitnessPage.tsx` 的动作行编辑）。快速记录一个想法要跨越 3 次点击 + 1 个弹窗。全站唯一的"零摩擦"入口是首页的快速备忘和 `parseQuickTask`（`src/utils/quickParse.ts`），但只覆盖任务。

**短板二：模块孤岛**

- `src/components/layout/CommandPalette.tsx` 的命令只有两类：`跳转` 与 `外观`，没有实体检索、没有创建动作。
- 搜索是**每页各写一份** `filterByKeyword`（Books / Dev / Fitness / Diet / Games / Writing 各引一次），只能搜自己模块。
- 没有标签系统：`src/types/index.ts` 里没有任何 `Tag` / `tags` 字段，也没有跨模块引用（只有 `ReadingSession.bookId`、`WorkSession.projectId`、`GameSession.gameId` 这类从属关系）。

**短板三：数据托底不足**

- 9 个 `persist()`（task / book / dev / writing / fitness / diet / game / theme / ui）都只传了 `name` + `version` + `migrate`，**没有 `onError`**；localStorage 写入超限（5MB 上限、Safari 隐私模式）时用户不会收到任何提示。
  —— **进度（2026-09-29）**：✅ 写入失败已分「读失败 / 写失败」两类提示，且数据主体已搬到 IndexedDB（配额按磁盘算，不再是 5MB），见 §9「V2.1 第八阶段：IndexedDB 存储层」。
- `public/` 目录为空：无 manifest、无图标、无 service worker → 不能安装成桌面/手机应用，断网不可用。
  —— **进度（2026-09-29）**：✅ 已补上，见 §9「V2.1 第七阶段：PWA 可安装与离线壳」。
- `migrateState()` 是**顶层浅合并**：只能补"store 根级"的缺失字段。数组内单条记录新增的字段（例如给 `Task` 加 `subtasks`）不会被回填，只能靠各页面写 `task.subtasks ?? []` 兜底——这就是 `src/types/index.ts` 里到处是"旧数据可能没有"注释的根因。

**短板四：缺"计划—专注—复盘"闭环**
V1 有：任务（列表/看板/四象限）、工时流水、阅读/游玩流水、热力图、趋势图。
V1 缺：时间盒、专注计时、每日总结、每周复盘、目标与达成率。`src/pages/StatsPage.tsx` 是"看历史"，不是"改进下一天"。

### 2.3 文档与实现的两处漂移（顺手修）

- `src/components/layout/navItems.ts` 里健身的描述是"训练记录与身体指标"，但 `src/types/index.ts` 没有任何体重/围度类型，页面上也没有入口。（已在 V2.1 第二阶段补上）
- `index.html` 的 favicon 指向 `/vite.svg`，而 `public/` 是空的 —— 也就是说不光没图标，那个图标本来就 404。（已在 V2.1 第七阶段换成自带的 `favicon.svg`）
- `docs/产品设计文档.md` 当时写着"不支持手机端"，但 P6-3-1 已做移动端适配。（**已修**：该文档 §1.3 现在写的是「移动端可用」，此条仅作历史记录。）

## 3. 功能建议

每条包含：目标 / 参考 / 数据影响 / 主要涉及文件 / 验收。优先级按"是否阻塞日常使用"排。

### P0 —— V2.0 必须做

#### F1 全局快速捕获（把录入压到一次输入）

> **状态：已在 V2.0 第二阶段落地**，实现细节与规则表见第 9 节。

- **目标**：任意页面 ⌘K → 输入一句中文 → 回车落库。例如 `明天 交周报 !高 #工作`、`跑步 30min`、`《置身事内》读到 120 页`。识别不了的输入**存成备忘并提示归类**，绝不丢内容。
- **参考**：life-os 的 capture（解析失败降级保存）、super-productivity 的 quick add。
- **做法**：`src/utils/quickParse.ts` 现在只解析任务；扩成"模块前缀 + 日期 + 优先级 + 标签 + 数值"的规则解析器（纯本地正则，不引 AI）。识别到模块就调对应 store 的 `add*`，否则落备忘。
- **涉及**：`src/utils/quickParse.ts`、`src/components/layout/CommandPalette.tsx`、各 `src/store/*.ts`、`src/components/ui/Toast.tsx`。
- **验收**：6 类前缀句式都能正确落库；无法识别时内容进入备忘且有提示。

#### F2 统一标签 + 跨模块全局搜索

> **状态：已在 V2.0 第三阶段落地**（数据层 commit `21a1cdd`，页面接入为本次提交）。
> 落地时对下面这条计划的调整写在**落地时调整**里，完整取舍见第 9 节。

- **目标**：一套标签贯穿所有模块；⌘K 能搜到实体（任务 / 书 / 开发项目 / 写作 / 训练记录 / 备忘），回车直达对应详情。
- **数据影响**：7 类实体加 `tags?: string[]`；新增 `lm:tags` 存标签颜色等元数据；`STORE_VERSION` → 12。
- **落地时调整**：`tags` 做成**必填**（由归一化层每次水合补齐，页面里不用写 `?? []`）；**不建** `lm:tags`
  元数据表，配色改由标签名哈希决定；版本号 bump 的是 `BACKUP_SCHEMA_VERSION`（10 → 11）而不是 `STORE_VERSION`，
  因为这是「数组内单条记录加字段」，升 `STORE_VERSION` 反而会让一次性迁移代码跑不到。
- **注意**：`migrateState()` 是顶层浅合并，**回填不了数组内单条记录的新字段**。这一步必须同时落地 D4 的归一化层，否则又要在每个页面写 `?? []`。
- **涉及**：`src/types/index.ts`、各 `src/store/*.ts`、`src/utils/search.ts`（扩成可复用的检索索引）、`src/components/layout/CommandPalette.tsx`。
- **验收**：搜"健身"能同时命中打了该标签的任务、书与项目；单测覆盖跨模块检索与去重。

#### F3 今日时间轴 + 专注计时

- **目标**：把今天的任务拖到 06:00–24:00 时间轴上形成时间盒；选中一项启动计时（番茄钟 / 正计时），结束后可一键完成任务，并把时长回填到开发工时 / 阅读 / 游玩流水。
- **参考**：super-productivity（时间盒 + 专注模式 + 休息提醒）。
- **数据影响**：新增 `src/store/focusStore.ts`（会话：`entityId`、`startedAt`、`minutes`、`mode`）；`Task` 增加可选时间盒字段。
- **涉及**：新 `src/components/timeline/`、`src/pages/TasksPage.tsx`、`src/store/taskStore.ts`。
- **验收**：拖拽生成的时间盒刷新后仍在；计时结束可一键完成并写入流水。
- **进度（2026-09-29）**：✅ 已完成 —— 数据层 commit `a362f59`，页面层见本次提交；首页新增仪表盘卡片「今日时间轴」（时间轴 + 专注计时）。详见 §9「V2.1 第三阶段」。

#### F4 习惯模块

- **目标**：新建习惯（每天 / 每周 N 次 / 自定义间隔），首页与习惯页都能**点格子直接打卡（无弹窗）**；用"习惯强度分数"（近期完成率加权）而非单纯连续天数；支持量化习惯（喝水 8 杯）。
- **参考**：uhabits 的强度模型、beaverhabits 的零弹窗打卡。
- **数据影响**：新增 `src/store/habitStore.ts`：`Habit { id, name, kind: 'binary' | 'count', target, schedule, logs: Record<dateKey, number> }`。
- **涉及**：新 `src/pages/HabitsPage.tsx`、`src/components/layout/navItems.ts`、`src/pages/HomePage.tsx`。
- **验收**：点格子即写入且可撤销；断签不清零；首页显示今日未打卡习惯。
- **进度（2026-09-29）**：✅ 已完成 —— 见 §9「V2.1 第一阶段：习惯养成」。

#### F5 体重与身体围度（兑现已有承诺）

- **目标**：体重 / 体脂 / 围度（胸腰臀臂腿）按日记录 + 趋势图 + "较上次 ±x kg"。
- **参考**：wger、Ryot 的 measurements。
- **数据影响**：新增 `src/store/bodyStore.ts`：`BodyMetric { id, date, weight?, bodyFat?, measurements: Record<string, number> }`。
- **涉及**：`src/pages/FitnessPage.tsx`、`src/components/charts/`、`src/components/layout/navItems.ts`（文案与实现对齐）。
- **验收**：新增一条体重后，趋势图与"较上次"数值正确。
- **进度（2026-09-29）**：✅ 已完成 —— 见 §9「V2.1 第二阶段：身体指标」。

- **参考**：dashy。
- **验收**：增删 / 重排后刷新保持；窄屏自动降为单列。

**落地时调整（原建议保留，这里说明为什么做得不一样）**

- **宽度分档，不做 1x1 / 2x2**：卡片高度全由内容决定，硬要「两行高」就得给每张卡定死高度，内容一多就出
  滚动条。改成 12 栏里的「小 4 栏 / 中 8 栏 / 宽 12 栏」，拿到同样的排版自由度又不用和高度打架；
  小 + 中正好凑满一行，用户也不用数格子。
- **只存 `{ id, size, hidden }`**：卡片叫什么、渲染成什么样都属于代码。以后改文案、换卡片内容都不会让用户
  排好的布局失效；新增卡片时 `normalizeDashboard()` 会把缺的补到末尾，用户不必手动点一次「恢复默认」。
- **编辑态才渲染「暂时没数据的卡片」**：平时「没有活动就不显示空热力图」这条规则保留（空卡片不占屏），
  但进编辑态一律显示成占位卡 —— 否则用户没法把一张当前没数据的卡片拖走或隐藏。
- **没做宽版布局（`max-w-7xl`）**：`Layout.tsx` 的内容宽度是全站共用的，只给首页放宽会出现「同一份内容
  在两个页面宽度不同」的割裂感。等 U2 双栏重新定义内容区宽度时一起处理。
- **今日时间轴 / 专注计时 / 目标达成环等新 widget 没做**：先把「可配置」这件基础能力铺好，新卡片属于
  V2.1 的内容增量。

**落地时调整**

## 5. 数据与工程建议

### D1 存储层：localStorage → IndexedDB（保留 localStorage 作为迁移来源）

- **为什么**：localStorage 约 5MB 上限、同步写入会卡主线程；一旦加入习惯日志（每天每习惯一条）、体重流水、正文快照与封面图，容量会迅速逼近上限。
- **怎么做**：引入 `idb-keyval`（约 600B gzip）或 `Dexie`；写一个 `createPersistedStore` 工厂（见 D4）把 zustand `persist` 的 storage 换掉，并在首次启动时把 `lm:*` 的旧数据一次性搬过去、成功后保留原 key 一段时间再清理。
- **约束**：迁移必须可回退、必须幂等；`docs/技术方案.md` 与 `STORAGE` 说明同步更新。

### D2 写入可靠性

- 给所有 `persist()` 补 `onError`（现在一个都没有）：写入失败要弹 Toast 并提示"数据可能未保存，建议立即导出备份"。
- 增加 `lastWriteAt` 与"待写入"指示；`Header` 的手动保存按钮已存在，可与自动状态合并成一个可信的保存状态。
- 用 `navigator.storage.estimate()` 在设置页给出"已用 / 可用"，超过 70% 时预警。

### D3 自动备份与落盘

- 现有：每次改动自动写 localStorage + 手动快照（`src/services/backup.ts`，保留 N 份）。
- 建议：① 按日自动生成一份快照，与手动快照分池、保留 14 天；② 提供"导出到指定文件夹"（File System Access API，Chrome / Edge 可用，纯本地不联网），记住目录句柄后每次打开应用静默写一份；③ 设置页显示最近一次备份时间与一键恢复。
- 兜底：不支持该 API 的浏览器降级为"每周提醒导出"。

> **进度（2026-09-29）**：✅ 三项全部落地。① 每日快照见 §9「V2.0 第一阶段」；② 导出到指定文件夹见 §9「V2.1 第九阶段」（句柄存 IndexedDB、开机静默写、授权失效不弹窗）；③ 设置页有最近写入时间与一键回滚。兜底文案已在设置页给出。

**几个刻意的选择**

- **标签配色不做配置**：`tagTone()` 按名字哈希出 6 档稳定配色，同一个词在任何模块、任何页面都是同一个颜色，
  不新增 `lm:tags` 存颜色。少一个数据源，就少一处「配置与数据不同步」。
- **不建「标签表」**：标签只存在各条记录自己的 `tags` 里。导入 / 导出 / 备份不用维护两张表的一致性；
  删掉最后一条带某标签的记录，这个标签自然消失，不会留下孤儿标签。
- **备忘不参与标签**：备忘是「先记下来再说」的自由文本，摘标签会破坏「原文一字不差」的承诺。
- **正文里的 `C#` 不算标签**：`extractTags` 用零宽断言 `(?<![A-Za-z0-9])[#＃]`，`#` 前面紧跟英文字母或
  数字时不识别；前面是汉字时仍然识别，所以 `写周报#工作` 也能摘出来。
- **训练 / 饮食这类流水只索引最近 100 条**（`STREAM_LIMIT`）：它们一年能积累上千条，全量进索引会让 `⌘K`
  的响应与内存占用都没有上界；100 条足够覆盖「最近在练什么 / 最近在吃什么」。
- **bump 的是 `BACKUP_SCHEMA_VERSION`（10 → 11），不是 `STORE_VERSION`（仍是 11）**：这是「数组内单条
  记录加字段」，归一化层每次 rehydrate 都会补齐；升 `STORE_VERSION` 反而会让一次性迁移代码跑不到 ——
  正是第一阶段修掉的那个坑。
- **Fitness / Diet 只做索引，没做卡片上的标签编辑器**：这两页的记录是「一条流水 + 多个动作 / 多种食物」的

### 顺手修掉的真实 bug：`todayKey()` 用的是 UTC 日期（已完成）

**几个刻意的选择**

- **一天一条，按日期 upsert**：体重是「每天量一次」的读数，同一天记两次多半是**修正**而不是两次测量。
  让 date 当主键，改一天就是改那一条，历史里不会出现两条同日记录把折线连成锯齿，「较上次」也不会拿同一天
  的两个值去比。把一天的值全部清空则等于删掉那天，而不是留一条空壳在趋势里占位。
- **趋势图不补 0**：`seriesByDay` 那套「按天补 0」适合次数类指标，用到体重上会把折线一路拽到 0。
  `bodyPoints()` 只取真实记录点，缺测的日子留给折线自己连；`LineChart` 也因此按 min–max 自适应，
  与「数量从 0 起算」的 `BarChart` 分工明确。
- **非正数等于「没记」**：0kg 不是读数。`readMetric()` 把 0 / 负数 / NaN / 非数字统一收成 `undefined`，
  于是「没记」与「记了 0」在数据里是同一件事，读取处不必到处写 `> 0`；schema 里也不能用 `.catch(0)`
  —— 那会在趋势图上凭空多出一个 0kg 的点。
- **边界只做「防脏」**：体重 / 围度上限 500、体脂上限 100，下界一律是 1。数值只做上限收口与一位小数，
  不按「成年男性合理区间」静默裁剪 —— 那是产品替用户改数据。
- **围度允许自建部位**：内置胸 / 腰 / 臀 / 臂 / 腿，备份里遇到别的键（例如「左腿」）原样保留，
  只按统一顺序排序（内置在前、自定义在后按字母序），不认识的键回退成键名显示。

**几个刻意的选择**

- **不引 workbox、也不上 `vite-plugin-pwa`**：这两个都会给一个「本地优先、依赖克制」的项目拉进一棵不小的依赖树，
  而我们要的东西（预缓存壳 + 网络优先的导航 + 哈希资源缓存优先）本身不到 100 行，读一遍就能改。
- **只缓存壳，绝不碰数据**：Service Worker 里没有 `localStorage` / `indexedDB` 的任何读写。
  缓存策略写错的代价是「页面旧了」，而不是「数据丢了」，这条边界必须守死。
- **导航请求是网络优先，不是缓存优先**：缓存优先在本地优先应用里很常见，但会让「部署了新版、用户却还在用旧版」持续到手动清缓存为止。
  这里让 `index.html` 每次先问网络，断网才回退缓存 —— 代价是离线首屏多一次失败的请求，收益是版本不会卡住。
- **maskable 单独出一张图**：Android 会把 maskable 图标按系统形状裁剪，直接拿普通图标去裁，圆角会被啃掉一块。

**几个刻意的选择**

- **手写 `kv.ts`，不引 `idb-keyval` / Dexie**：这两个库加起来能替我们省下的代码不到一百行，但语义（多后端合并、首启搬家、
  打不开就降级）还是得自己写；「本地优先、依赖克制」的项目不值得为这点胶水拉一条依赖，更别说这条依赖要是坏了，坏的是数据层。
- **主题 / 密度仍留在 localStorage**：`index.html` 里那段首屏防闪烁脚本是**同步内联**的，必须能在第一次绘制前读到值。
  IndexedDB 只有异步 API，把主题放进去等于每次刷新先闪一下默认色。所以 `SYNC_KEYS = ['theme', 'ui']` 显式留在同步后端，其余全搬。
- **老数据只写不删**：搬家时把 localStorage 那份原样留着，代价是同一份数据在迁移期占两份空间，收益是「新版本读到脏数据」或
  「用户想退回旧版本」都有退路。等哪天确认不再需要，再单独做一次显式清理，而不是在搬家那一刻顺手删掉。
- **首屏等待封顶 1.5s**：纯等 `hasHydrated()` 在正常情况下是毫秒级，但只要有一次 IndexedDB 打开被阻塞（隐私模式、磁盘满、
  另一个标签页占着升级锁），就会无限等下去。宁可 1.5s 后先把界面画出来、让后到的数据再补进来，也不留一个「永远转圈」的可能。
- **`measureAppStorage()` 只统计主后端**：迁移期 localStorage 里那份是历史副本，把它算进占用会让数字凭空翻倍，
  用户会以为「我明明没存多少怎么占这么多」。占用说的是「真实生效的那份」，历史副本不该计入。
- **`setItem` 不透出 promise**：zustand 的 `persist` 用 `(...args) => { set(...args); return setItem(); }` 包住 set，
  返回值会变成**每个 action 的返回值**。一旦这里透出 promise，所有 action 都变成「返回 promise 的 action」，
  React 的 `act()` 会把它们当异步动作处理，测试时序全乱。所以 `persistStorage.setItem` 返回 `void`，async 实现单独抽成 `writePersisted()`。

**新增测试**：`src/store/kv.test.ts` 12 条（内存假后端 + 极简 IndexedDB 替身 `installIndexedDbStub()`：key→后端路由、首启搬家、

**几个刻意的选择**

- **句柄单独开一个库**：`FileSystemDirectoryHandle` 只能结构化克隆，JSON 序列化不了，所以它没法跟主题一起塞进
  localStorage。那就干脆放在自己的 `life-manager-handles` 库里；也正因为如此，退回 localStorage 的环境里
  这个功能直接判定为「不支持」——而不是「假装支持、重开就忘」。
- **固定文件名，不做轮转**：每次覆盖 `life-manager-auto-backup.json`。这个目录是用户自己选的（同步盘、移动硬盘），
  在那里堆一串日期文件是要用户自己收拾的；「总是最新的一份」才是它存在的意义。要历史版本，应用内的快照池负责。
- **开机只在「已经授权」时才写**：`queryPermission` 不是 `granted` 就跳过。浏览器要求目录授权由用户手势触发，

- **写失败一律吞掉**：U 盘拔了、目录被删、磁盘满 —— 开机时这些只意味着「这次没更新备份」，
  不该升级成「应用启动报错」。设置页会显示最近一次写入时间，新鲜度是可查的。
- **必须先水合、再读数据**：`readAllData()` 读的是内存 store。水合完成前调用会拿到一份空数据，

**几个刻意的选择**

- **先做逻辑层，不做「一个大组件」**：`EntityListView` 听起来是一次抽干，但六页的**渲染部分**其实各不相同
  （游戏是卡片网格 + 详情栏，读书是双栏 + 笔记面板，饮食是按日期分组）。硬套一个渲染壳，要么壳里塞满
  条件分支，要么把页面特有的东西挤到配置对象里 —— 两种都比现在难读。
  这几页真正重复的是**逻辑**：两个 useState、一遍状态筛、一遍关键词筛、一个计数、一句「是空库还是没筛出来」。
  所以先把这块抽成 hook，渲染仍归页面。
- **空态是一个独立组件，而不是 hook 的一部分**：文案要带模块名（「书单还是空的」/「游戏库还是空的」），
  而且主操作是页面自己的按钮。hook 只负责回答「是哪种空」，怎么讲由页面决定。
- **`searchFields` / `statusOf` 要求是稳定引用**：它们进 `useMemo` 的依赖，所以示例里都写成模块级常量
  （`const bookSearchFields = (book: Book) => [...]`）。写成内联箭头也不会算错，只是每次渲染都要重筛一遍 ——
  hook 的注释里写明了这一点，因为「看起来在缓存、其实缓存永远失效」是最难发现的一类浪费。
- **`clearFilters` 只回到「全部」，不回到 `initialFilter`**：它对应空态里那个「清除筛选」按钮，
  用户的意图是「让我看到东西」，而不是「回到我刚进页面时的筛选」。

**第 2 块：每模块独立分析**

原来统计页只有「任务完成数」「摄入热量」两张趋势图，其余模块只出现一根「记录条数」的分布条 ——
读书的时长、健身的容量、写作的字数全被折成「条数」，看不出各自练成了什么样。这一块给每个模块一张自己的图：

| 模块 | 指标 | 为什么是这个 |
| --- | --- | --- |
| 读书 | 每日阅读分钟 | 时长才说明读了多少，条数只说明打开过 |
| 健身 | 训练容量（Σ 组 × 次 × 重量） | 次数不分轻重，容量才看得出「练得更重了 / 只是多记了几笔」 |
| 饮食 | 每日蛋白质（g） | 热量上面已经有一整张图，这一格换一个维度 |
| 开发 | 每日投入工时 | 已有流水字段，按天汇总即可 |
| 写作 | 每日写下的字数 | 没有流水，按保存正文留下的快照推算 |
| 游戏 | 每日游玩时长 | 与开发、读书同一套流水 |

每张卡是「区间合计 + 有记录天数 + 单日最高 + 自己的柱状图」，跟随时间范围与聚合粒度，和页面其余部分同一套口径。

**这一块的几个选择**

- **取代了原来固定「近 8 周」的三张图**：那三张不管区间选择器怎么改都纹丝不动（工时 / 阅读 / 游玩各一张），
  和旁边的「最近 30 天」摆在一起只会让人以为坏了。现在六个模块共用同一个区间与聚合粒度，
  想看长周期切到 90 天 / 全部就行，信息一点没少。
- **没有流水的模块直接不出现**：与其摆一排全是 0 的图，不如让这一块随用户实际在用的模块长出来。
- **健身看容量、不看次数**：自重动作（重量 0）的容量算出来就是 0，这是刻意的 ——
  与其把「三组俯卧撑」折算成一个编出来的公斤数，不如让容量只反映真的加了重量的部分，卡片也写明单位是 kg。
- **写作的「写下字数」是估算**：没有按天流水，只能靠保存正文时留下的快照（滚动保留最近 20 版）取相邻两版的差，
  记在后一版那天。所以老项目窗口外的存量会被算进它第一个已知版本的那天，删改也不产生负增量 ——
  卡片副标题直接写「按保存快照推算」，不假装它和流水一样精确。

**顺手修掉的真实 bug：全 0 序列的图表读成「合计 0，最高 1」**

`BarChart` / `StackedBar` 都要算柱高比例，除数用 `Math.max(1, ...values)` 兜住除零 —— 但这个数又被写进了
`aria-label` 的「最高」一项。于是一段有日期、却一条记录都没有的区间（比如空的一周）会被读成
「合计 0 次，最高一天 1 次」，前后自相矛盾。修法是把这一个数拆成两个：`scale` 只服务画图（保住非零下界），
描述里另算 `peak`（真实最大值，全 0 就是 0）。`charts.test.tsx` 补了「全 0 柱状图 / 全 0 堆叠柱」两条用例，
把实现临时改回 `scale` 会准确失败在这两条上。

**顺手修掉的第二处：按周 / 按月聚合的图仍念「单日最高」**

`BarChart` / `StackedBar` 的无障碍描述里写死了「单日最高」「最高一天」，可它俩现在也用来画按周、按月聚合的序列 ——
统计页 90 天档下，「本周做了 5 件事」会被念成「单日最高 5」。修法是由调用方把聚合粒度报进来（新增 `ChartBucket`
与 `bucket` 属性），措辞留在图表内部：柱状图说「单日 / 单周 / 单月最高」，堆叠柱说「最高一天 / 一周 / 一月」。
任务页那张「近 8 周每周完成任务数」也补上了 `bucket="week"`，顺带一起修正。

**顺手修掉的排版回归：宽操作区把页头标题挤成一列窄条**

真机截图才看出来：选中「自定义」后，页头标题块被压到约 80px 宽，描述「1/5 至 1/25 的活动趋势与各模块进度」
折成四行。根因在 `PageHeader`（15 个页面共用）：操作区写的是 `shrink-0` —— 宽度不够时它一步不让，
只能由标题让路；而标题是 `flex-1`（`basis: 0%`），于是被压到快没有。修法是给操作区去掉 `shrink-0`、
补 `min-w-0`，并给标题块加 `basis-56` 当换行阈值：窄容器下操作区自动落到第二行，标题独占第一行。
1280px 下 `今日计划` / `饮食` 等页一行未变（已截图核对），375px 下按钮组与日期框分两行、都可读。

**第 3 块：图表导出 PNG**

统计页的图以前只能靠截图，截图会带上浏览器边框、侧栏与缩放误差。这一块给每张图表卡的标题栏右侧加了一个
导出按钮，点一下把**整张卡**（标题、副标题、单位、图例、坐标轴文字）落成一张二倍图，
文件名形如 `life-manager-任务完成趋势-2026-09-30.png`。

**这一块最要紧的决定：拍照，而不是按数据重画**

按数据重画到 canvas 是更「正统」的做法，但统计页的柱状图与堆叠柱是 HTML 元素拼的（不是 SVG），
要为每种图各写一套 canvas 绘制代码，等于把配色、圆角、间距、刻度再实现一遍 —— 以后改一次样式就得改两处，
迟早画出来的和屏幕上看到的不一样。所以这里走的是「拍照」：深拷贝卡片 DOM → 把每个节点的 `getComputedStyle`
内联进 `style` 属性 → 整体塞进 `<foreignObject>` 交给 SVG → 交给浏览器渲染成图 → canvas 画出二倍图 → `toBlob` 落地。
屏幕长什么样，导出来就是什么样。

**这一块的几个选择**

- **样式必须内联**：Tailwind 的类名定义在外部样式表里，单独把 DOM 丢进 SVG 是不带样式的，导出来会是一堆
  没颜色没间距的黑字。所以逐个节点抄一遍计算样式；自定义属性（`--lm-*`）不用抄 —— 计算值已经把 `var()` 解开了。
- **导出按钮自己不进图**：按钮带 `data-export-skip`，拍之前从副本里摘掉。
- **先铺一层卡片底色**：深色主题下卡片是深色的，不铺底的话透明区落到别处会变成白底黑字（浅色 / 深色都真机验过）。
- **拿不到 canvas 就早点说**：先要 `getContext('2d')`，拿不到直接抛「这个浏览器没有提供 canvas，导不出图片」，
  不去白费功夫抄样式、加载图片。
- **失败只提示不抛**：截图依赖浏览器的 SVG / canvas 能力，个别环境会不给。这时给一条红 toast，页面照常，
  不因为一次导出崩掉。
- **`Card` 转发 ref，`ExportableCard` 自己持有它**：导出的是卡片本身（不带外层列表的留白与间距），
  所以让卡片自己拿着 ref，而不是让调用方给每张卡都建一个 ref 再往下传。

**新增测试**：第 1 块 —— `pages/StatsPage.test.tsx` 3 条（自定义区间挪到历史段后标签 / 图 / KPI 同步、
起止填反按更早那端算、「近 7 天日均热量」不随区间漂）；`components/charts/charts.test.tsx` 2 条

第 2 块 —— `utils/moduleInsights.test.ts` 新文件 13 条（训练容量与负数脏数据、逐日写作净增字数含同一天多次保存

**几个刻意的选择**

- **心情用 0 表示「没记」，不是 1**：和「今天很糟（1）」是两件事，不能都算成 1。
  缺的日子在曲线上**不补 0** —— 补出来的 0 会把折线拽到底，读起来像「那天心情极差」，
  而真实情况只是那天没记。
- **按周 / 按月聚合求均值，不是求和**：一周七天都是「一般」不该读成 21 分。所以没有复用柱状图的
  `bucketize`（那边求和是对的：一天的次数加起来就是那一周的量），另做了一套求均值的聚合。
- **心情用有方向的配色**：两头发红、中间中性、好的一头走绿。图表那套分类色（`chart-1..8`）看着整齐，
  但读不出「5 比 2 好」。
- **清空就是删除**：心情归 0、标签清空、正文删光之后保存，这条记录直接消失 ——
  留一篇空白日记除了把列表撑长没有任何意义。删除走带「撤销」的提示，撤销用整表快照还原。
- **未保存的草稿按日期留在内存里**：切到别的日期再切回来，写了一半的字还在。
  直接让表单跟着日期重建（复盘页那种写法）在日记上是危险的 —— 很可能写了几百字，只是想翻回昨天看一眼。
  真正落库仍然要按保存，所以不会偷偷把「清空到一半」的状态写进去。
- **趋势窗口取近 30 天**，与首页热力图同一个口径；周 / 月聚合的日期键仍取周一 / 当月 1 号，和别的图对齐。

**补记（2026-09-30）：打字机滚动计入软换行**

原来「一个换行符 = 一行」。这在中文短行正文里没事，但一段**没有换行符的长文**
（贴进来的英文段落、一整个中文段落）会被当成 1 行，`contentHeight` 算成一行高、
`maxScroll` 恒为 0 —— 打字机滚动在这类正文里**完全失效**，光标走到哪都不滚。

改法：先按 textarea 的实际可用宽度把每行折成**视觉行数**，再定位。

| 项 | 状态 | 说明 |
| --- | --- | --- |
| 折行计算 | ✅ | `utils/typewriter.ts` 新增 `charWidthUnits` / `lineWidthUnits` / `wrappedLineCounts`；CJK 与全角标点算 2 格、其余算 1、tab 按 8 格对齐 |

**一个实测挖出来的坑：标尺不能用数字。**
第一版用 `'0'.repeat(20)` 量半角宽，结果在 Microsoft YaHei 下 `0` 宽 7.55px、
而真半角宽是 7.0px —— 高估 7.8%，6800 字的长文折下来多算 6 行，估算/实测 = **1.096**。
改成拿 **CJK 方块宽度除以 2**（CJK 字形是标准方块，宽 = font-size）之后落到 **1.014**，
只剩一行高（20px）的残差，那是 `scrollHeight` 对末行换行的口径差，无关紧要。

### V2.1 第十九阶段：分模块导出（F15·已完成）

**要解决的事**

「导出数据」原来只有一个按钮，导出的是全量 JSON。想拿一批任务去做透视表、想把日记导进笔记软件、
想只备份某一类数据，都得先导出全量再自己拆。

**做法：一张登记表，三种格式都从它推出来**

给 21 个模块 × 3 种格式手写 63 个导出函数是不可接受的 —— 加一个字段要改三处，迟早改漏。
所以 `src/services/moduleExport.ts` 里只有一张 `MODULE_EXPORTS`：每个模块声明「列名 + 取值函数 +
Markdown 标题字段」，CSV 与 Markdown 共用同一份列定义。JSON 不需要列定义，直接导原始记录。

单元格渲染收在同一个 `cellText` 里，所以不会出现「CSV 里有值、Markdown 里空白」这种漂移。

**两个模块只给 JSON**

`devProjects` 与 `writingProjects` 标为 JSON-only。它们挂着子任务数组、里程碑、开发日志、正文与
版本快照 —— 压成一行 CSV 会把有用的东西丢掉，而且丢掉之后那份文件既不能读也导不回去。
UI 上两个按钮直接禁用并显示原因（`jsonOnlyReason`），不是点了才报错。

**日记不平铺**

日记走 `prose` 分支：把正文塞进表格格子会把换行压平，那是把「一篇日记」变成「一行摘要」。
它按 `## 日期` 分节展开，正文原样保留。

**单模块 JSON 要能导回去**

这是它跟「随便存一份 JSON」的区别。格式与全量备份同源 —— 同样的 `app` / `schemaVersion` /
`exportedAt` / `data` 信封，只多一个 `module` 字段。这样 `parseBackup` 不用学一套新格式就能认出来，
**全量导入的代码路径一字未动**，挂在它上面的 51 条既有单测照常绿。

完成勾选框，用宽口径的 `isTypingTarget` 会让 `j` / `k` 直接失灵。

**刻意不做的部分**

- **开发 / 健身 / 饮食三页不接列表导航**：它们是按日期分组的流水与时间轴，不是同构的行列表，硬套会做出六套
  不一致的手感；看板另有一套 —— `KanbanBoard` 的拖拽本来就走 `@dnd-kit` 的 `KeyboardSensor`（空格拾起 / 方向键 / 空格放下），
  这次只给它补了测试（jsdom 里 rect 全是 0，得先把各列的坐标摆出来才测得到）。
- **不做「排序」公用件**：各页排序维度差异太大，抽出来只会是一堆配置分支。
- **图表不做跨点位的一句话摘要**（「最近 30 天共 42 次活动，最高为 3 月 12 日 5 次」那种）：现有 `aria-label`
  已经给出合计与带日期的极值，够用；等有人真的需要再上。
- ~~**编辑弹窗与饮食 / 健身多字段弹窗的回车提交**（U7 未完成的部分）~~ —— 已在第二十四阶段做完，见下。
- **`j` / `k` 不进全局快捷键表之外的场合**：命令面板里那套「`j` / `k` 会和打字冲突」的取舍没变（见 §4 U3），

### V2.1 第二十四阶段：弹窗回车提交铺满（U7 尾巴 · 已完成）

**要解决的事**

「回车即提交」之前只覆盖了五个新建弹窗。真正天天用的是另一半：任务的编辑右栏、书房里给书打分写短评、开发项目里记一条流水、
健身记一次训练、饮食记一餐 —— 这些多字段面板都还只有「点按钮才存」。人填完最后一项顺手回车，页面不动，
只会以为是自己没点中。

**① 抽一个 `SubmitForm`，把三条约定固定下来**

`src/components/ui/SubmitForm.tsx`，19 处表单共用。三条约定：

- **表单树里必须有一个提交按钮**。隐式提交（在输入框里按回车）的前提就是这个；只把 footer 的按钮用 `form={id}`
  关联过来，覆盖的只有「点击」那条路径，回车仍然什么都不会发生。所以壳里放了一个 `sr-only` 的提交按钮：
  对浏览器而言它就在表单里，对人而言不可见、不进 Tab 序、读屏也不念。
- **footer 里那个按钮写成 `type="submit" form={id}`，不要再挂 `onClick`** —— 两条路径都通到同一个 submit 事件，
  挂上 `onClick` 会提交两次。上一阶段正是漏了这一条才留下双提交的坑。
- **`noValidate` 不能省**（下面单独说）。

**② 七页 19 处接入**

| 页面 | 表单 |
| --- | --- |
| 任务 | 新建 / 编辑右栏 |
| 书房 | 添加书 / 评分短评面板 / 记录阅读 |
| 游戏 | 添加游戏 / 记录游玩 / 详情面板 |
| 开发 | 新建项目 / 编辑右栏 / 加任务 / 记流水 |
| 写作 | 新建项目 / 笔记 / 正文 |
| 健身 | 新建计划 / 记录训练 / 记录身体数据 |
| 饮食 | 记录饮食 |

**③ 真机踩到的坑：原生校验会静默吃掉提交**

单测全绿之后 e2e 挂了：饮食弹窗填「燕麦 + 233 kcal」点保存，记录没落库。查下去发现表单是 `invalid` ——
热量框是 `step=10`，233 不整除，`stepMismatch` 成立。**浏览器对不满足原生约束的表单，会直接拦下提交，
连 `submit` 事件都不发**，所以既没有报错也没有任何反应，人只会以为按钮坏了。

这个坑单测照不出来（jsdom 不跑那套校验流程），而且它是**上一阶段把 `<div>` 换成 `<form>` 时引入的回归** ——
换壳之前点击走 `onClick`，根本不经过校验。`min` / `step` / `required` 在这里是给输入框自己的提示，
校验本来就归页面自己管（`canSave` 那一套），所以 `SubmitForm` 上加了 `noValidate`，把原生校验关掉。

**④ e2e 补一条真机用例，顺带修了键鼠助手**

`diet-enter-submit`：真键盘在名称框里敲回车 → 记录落库、弹窗自动收起、焦点回到页面。它同时守住了上面那个坑
（那条记录的热量就是 233）。

写这条用例时发现 `session.key()` 少了一样东西：**不带 `text` 的 `keyDown` 只有 keydown / keyup，
不会产生 keypress**，而回车提交表单这类默认动作是挂在 keypress 上的 —— 焦点、键码全对，页面一动不动。
助手补了可选的 `text`（回车传 `text: '\r'`），`e2e/README.md` 里记了一行。

| `src/pages/{Tasks,Books,Games,Dev,Writing,Fitness,Diet}Page.test.tsx` | +10 | 编辑右栏 / 评分短评 / 详情面板 / 多字段记录弹窗各一条：框里回车直接存 |

### V2.1 第二十五阶段：写作卡片那一行控件错位（真机复查）

**现象**

写作卡片上「字数 / 目标 / 状态」三个控件不在一条线上。量出来的数字很干脆：字数与状态的上边缘都在
517，目标那个框在 495 —— 高了整整 22px，正好是它下面那行小字（`hint="0 表示未设置"`）的高度。
这一行是底对齐（`items-end`），谁的框高谁就被顶上去，顺带把旁边的「更新于」也带得没处站。

**为什么单测全绿还是歪的**

jsdom 里 `getBoundingClientRect()` 全是 0。单测只能断言「DOM 里有没有那个元素」，
断言不了「它长在哪儿」—— 这类错位只有真机量得出来。

**改法：那行小字去掉**

`hint="0 表示未设置"` 撤掉。去掉之后三个框回到同一条水平线（都在 517～555），卡片也矮了 22px。
「目标填 0 就是没设目标」这层意思不再印在卡片上。

**新增 `e2e/cases/layout.e2e.mjs`**

第一份专门量几何的用例（`writing-card-row`）：造一条项目 → 量三个控件的 `top` / `bottom` 是否齐，
顺带断言卡片里不再出现那行字。把 hint 加回去它立刻红（`字数 517，目标 495`），护栏是实的。
`e2e/README.md` 的目录与纪律都补了一笔。

**顺带修掉一处用例之间串味**

这条用例单跑是绿的，全量跑却红：「目标」比「字数」低 50px（38 高 + 12 间距 ＝ 折行了）。
不是它自己的问题 —— 窄屏用例把视口改成 375 就不管了，排在后面的宽屏用例于是长在窄屏上。
视口和存储是同一类全局脏东西，所以 `beforeEach` 里补了一步「压回 1440×1100」，
`e2e/README.md` 的纪律里记了一条：**改了视口要还回来**。

**测试**：单测不变 **1455**；e2e 31 → **32**（新增 `writing-card-row`）。
首屏 gzip 164.5 KB / 300 KB 预算。
