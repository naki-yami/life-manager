# 导航收敛用嵌套路由，旧路径永久保留

主导航要从 13 项收敛到 8 项 —— 书房 / 健康 / 统计与复盘 / 成长 四个宿主，各带 2–3 个子页。
我们决定采用**嵌套路由 + 宿主薄壳**：子页真实存在于 URL 里（`/study/books`），宿主只负责渲染
子页签条与 `<Outlet />`；所有旧路径（`/books`、`/writing`…）以 `<Navigate replace>` **永久**保留；
这一轮**不合并任何 store**，数据层零改动。

## 考虑过的其他做法

- **原路由不变，页内互相挂兄弟链接**：URL 不分层，命令面板、底部 Tab、`g+数字` 的收敛全都要靠特判。
  嵌套路由一次到位，而且宿主给「跨子页联动」（如健身与饮食共用一个日历）留了干净的挂载点。
- **旧路径只留一个过渡期再删**：PWA 场景下「确认没有旧链接在飞」永远无法确认。永久保留的成本只是
  路由表里几行，删掉却可能让书签和已安装的 PWA 快捷方式失效。
- **顺手把读写的 store 也合并**：合并导航是信息架构问题，合并数据是迁移问题。两者一起做，
  出问题时不知道是哪一层；而迁移有数据丢失风险，这一轮不值得。

## 后果

- `findNavItem` 是精确匹配，`/study/books` 会落空，必须归约到宿主，否则顶栏标题与读屏播报
  **静默降级**（不是 404，比 404 更难发现）。
- 子页需要一份独立于 `NAV_ITEMS` 的真相源（`MODULE_TABS`）：`NAV_ITEMS` 收敛到 8 条之后，
  里面不再有子页路径，「过滤 `NAV_ITEMS` 得到签条」这条思路走不通。
- 子页之间切换会 unmount / mount，子页内部状态（搜索框、筛选、滚动位置）会重置。已确认可接受。
- 切换子页走 push，与侧栏、底部 Tab 的点击行为一致；后退键会依次回退访问过的子页。
