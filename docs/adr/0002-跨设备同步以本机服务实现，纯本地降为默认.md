# 跨设备同步以本机服务实现，纯本地从硬约束降为默认

「纯本地、不引入后端与云 API」是 V1 定下的硬约束（`docs/Life-Manager-V2-优化建议.md` §8）。它带来数据
主权与零运维成本，代价是所有多设备场景只能靠「导出到同步盘文件夹」绕开；而那条路没有合并语义 ——
两台设备各改一份，就只剩「覆盖」或「合并」两种粗糙选择，且回答不了「谁改得更晚」。

我们决定**解除这条硬约束，改为：纯本地是默认形态，跨设备通过自建同步服务可选开启**。同步服务只做
单用户多设备，不做账号体系、不做分享、不做协作。冲突语义第一版取**按条目 last-write-wins + 删除留墓碑**，
字段级合并留到有真实冲突数据之后再谈。服务端存储沿用现有备份 JSON 的形状，不重新设计数据模型。

**服务运行在本机**，而不是外部 VPS。这一条是本次拍板的核心，代价见「后果」。

## 考虑过的其他做法

- **服务跑在外部 VPS**：隔离性最好 —— 断电、C 盘写满、Windows 自动重启都不会同时打掉服务与客户端，
  「线上运行」那一段能补得最完整。否决理由：数据要离开本机，与「个人数据不经过别人服务器」的初衷
  冲突，且新增一处需要信任的托管方。代价是本机方案的隔离性缺失（见「后果」），属于**知情接受**。
- **维持纯本地，把同步盘文件夹做厚**（给它加合并）：保持在定位内，但合并需要版本与墓碑，而同步盘
  只提供文件级原子性 —— 等于自己实现一半同步协议，却拿不到服务端的时钟与事务。省下的只有一台服务器。
- **用现成的同步服务**（第三方 BaaS 或 CRDT 托管）：省掉自建，但把「你的个人数据不经过别人服务器」
  这条 V1 的核心卖点直接交出去，与解除约束的初衷相反。
- **一上来做完整 CRDT**：语义最正确，但对单用户多设备是过度设计。单用户场景的并发窗口极小，LWW 足够，
  出问题时也更容易向用户解释。
- **先做字段级合并、再做同步层**：合并逻辑需要真实的冲突样本才能定对，先做等于凭空设计。

## 后果

### 定位与文档

- 「数据只在你自己的浏览器里」这句话**不再无条件成立**。`README.md`、`CONTEXT.md`、产品文档里所有
  相关表述都要改，并明确写出「同步关闭时仍然是纯本地」。
- 现有「导入时三种合并策略」（`merge` / `overwrite` / `append`，见 `src/services/backup.ts`）与新的同步
  合并是**两套语义**，且现有 `merge` 纯按 id 存在性跳过、从不比较时间或内容。需要在文档里分清楚，
  避免用户在导入时误判为同步。

### 本机运行的三条代价（知情接受）

- **第二份存储必须离开这台机器。** 服务在本机、数据也在本机，若「第二份」还放在同一台机器，同步服务
  不但没有降低丢数据风险，反而新增了一处与原数据同生共死的副本。两台 SSD 均为无缓存杂牌盘、C 盘余量
  不宽裕，这条不是理论风险。
  **载体取「配置里指定的一个文件夹路径」**：服务端按配置的路径周期写一份整库副本，指向用户已经选好的
  同步盘目录即可 —— 不引入新依赖、不产生新成本、数据不离开用户自己选的目录。代价是依赖该同步盘的
  客户端在运行，属于用户已经信任的一环。
  **不能复用客户端的 `folderSync` 授权**：那条路用的是 File System Access 目录句柄，句柄存在浏览器的
  IndexedDB 里（`src/services/folderSync.ts:13`），授权还必须由用户手势触发（同文件 `:15`）；本机服务
  是独立进程，既拿不到也存不了这个句柄。所以服务端走**自己的配置与权限模型**：路径由用户在服务配置里
  给出，服务进程只读写这一个目录，与客户端的 `folderSync` 是两条互不相干的通道。
  **文件名不共用**：客户端那条固定写 `life-manager-auto-backup.json`（`folderSync.ts:19`），服务端另用
  一个文件名（`life-manager-server-replica.json`），避免同目录里两边互相覆盖。
  **启动时校验「第二份确实离开了本机」**：配置的路径与数据目录落在同一卷时明确告警 —— 否则这条代价白付。
  外部对象存储被否决：它要求数据经由第三方托管，与「跑本机」的初衷相悖。
- **「线上运行」补不全。** 部署、日志、可用性探针、进程崩溃自启、开机自启、发布回滚都能补；但断电、
  C 盘写满、Windows 自动重启会**同时**打掉服务与正在使用的客户端。隔离性是本机方案拿不到的。
- **多设备带可用性前提**：手机要读数据，家里这台机器必须开着。这是方案固有代价，不能靠工程绕开。

### 版本与冲突元数据

- `STORE_VERSION`（`src/store/persist.ts:29`，当前 `12`）与 `BACKUP_SCHEMA_VERSION`
  （`src/services/schemas.ts:32`，当前 `19`）是两个**互不相干的计数器**，且备份信封只携带后者。
  同步引入的**记录版本**是第三个概念，必须明确它与前两者的关系，不能指望任一计数器代为表达。
- 冲突元数据（记录版本 / 墓碑 / 设备标识）新增字段时，**走既有的归一化层，不要靠 bump 版本号**。
  `persist.ts:21-24` 已经把这条原则写死：根级结构变更靠 bump 触发 `migrate`，而「数组里单条记录新增
  字段」必须交给挂在 `merge` 上的 `normalize`（每次 rehydrate 都跑且幂等）；版本号一旦升到最新，
  写在 `migrate` 里的补字段代码就再也不会执行。
- 现状核查（2026-10-02）：`tombstone` / `deviceId` / `deletedAt` 在 `src/` 下**零匹配**；`updatedAt`
  仅存在于写作项目、复盘、日记三类记录（`schemas.ts:239`、`:482`、`:504`），且由各 action 手工维护，
  多个 `updateX` 直接绕过。**第一版取按条目 LWW 就是为了不依赖这个不可靠的字段** —— 每实体补
  `updatedAt` 是字段级合并的前置改造，属于 V2.1。

### 数据安全

- 数据多了一处可能丢的地方。同步服务必须自带备份与回滚，不能只依赖客户端的自动快照。
- 「取消打卡即删掉那天的记录，不留 0 占位」（见 `CONTEXT.md`「打卡」）**与墓碑并不冲突**（更正于
  2026-10-02）：打卡日志是习惯记录内部的 `日期 → 数值` 映射，取消打卡只是该记录的一次字段变更，
  随按条目 LWW 一起传播，不产生墓碑。墓碑只服务于整条记录的删除 —— 先前的写法把它当成需要墓碑的
  删除，是错的，并且会给实现凭空加一层没有对应物件的机制。

### 鉴权与暴露面

- **只监听本机**：同步服务默认绑定 `127.0.0.1`，不监听 `0.0.0.0`。要服务手机就必须显式放开，并在
  放开时给出提示 —— 这一步不能被静默默认掉。
- **单一预共享令牌**：不做账号体系（见 `CONTEXT.md`「同步」「令牌」「设备」三条），鉴权取一枚服务端首次启动
  生成、客户端在设置页填一次的预共享令牌。令牌与设备标识是两件事：令牌回答「你能不能连」，
  设备标识回答「这条改动是谁写的」。
- **README 的措辞以此为据**：`README.md` 里「开启同步后需要一个访问令牌」说的就是这枚令牌；在实现落地前
  文档不承诺更多 —— 不做注册、不做分享、不做协作。

### 回滚条件

同步是可选开关，回滚**不动客户端数据**：关掉开关即回到纯本地、零网络请求。

- **数据受损** —— 任何一次同步导致记录丢失或字段被改坏（LWW 取错一侧、墓碑误删可见记录）：立即停用
  同步、以客户端自动快照回滚，并冻结该版本直到根因明确。这条优先于其他一切。
- **服务器副本写不进去** —— 第二份存储连续多日写失败（同步盘客户端没开、路径失效、权限丢了）：
  此时同步已不再降低丢数据风险，收益归零，停用而不是继续跑。
- **维护成本超过收益** —— 服务端需要频繁人工介入（进程不自启、日志要人肉看、崩溃后手动修复），
  即「线上运行」补不全这条代价兑现成了日常负担，退回纯本地。
- **定位漂移** —— 出现「必须开同步才能用」的功能（例如依赖服务端时钟才成立的特性）：与本 ADR
  「纯本地是默认形态」的前提冲突，先改回默认可用再谈同步。

回滚动作固定为：客户端关闭同步 → 导出一次整库备份 → 删除本机服务的目录副本与令牌。
