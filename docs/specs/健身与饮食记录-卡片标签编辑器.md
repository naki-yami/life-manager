## Problem Statement

健身与饮食这两页的记录，已经有「标签」这个数据字段，也已经被全局搜索索引到了（在搜索框里敲 `#胸`、`#外食` 都能搜到对应的训练与饮食记录），但**页面上完全看不到、也改不了**。

后果是：标签只能靠最初的写入路径带进来（健身计划模板、饮食条目里预设的），事后想给一笔已经记下来的流水补个「腿」「加班餐」，没有任何入口。用户能搜到一个标签，却没有任何办法在页面上管理它——标签体系一旦需要调整，只能放弃或者绕路。

这与另外六个模块（读书、游戏、任务、写作、开发项目、日记）不一致：那六处都有卡片上的就地标签编辑器，只有健身与饮食缺这一块。

## Solution

在健身与饮食两个页面的记录卡片上，补上和其余六个模块**完全一致**的就地标签编辑器：

- 收起时显示该条记录已有的标签（只读的一排标签片）；
- 点一下展开输入框，回车或逗号收下标签，可以增删；
- 输入时给出全站标签建议，跟别处共用同一份建议来源；
- 点「完成」收起，改动立刻落库，不需要进编辑弹窗、不需要点保存。

改完之后，「标签」在健身与饮食里从「只能被搜到」变成「看得见、改得动」，和其余六个模块对齐。

## User Stories

1. 作为一个记录健身流水的用户，我想在训练记录卡片上看到这笔流水已有的标签，这样我不用打开编辑弹窗就知道它被归到了哪个部位。
2. 作为一个记录健身流水的用户，我想在卡片上直接给一笔训练补一个「腿」标签，这样我事后整理训练分类时不用绕进编辑表单。
3. 作为一个记录健身流水的用户，我想在卡片上删掉一个打错的标签，这样标签体系不会随着时间累积脏数据。
4. 作为一个记录饮食的用户，我想在饮食记录卡片上看到这笔记录已有的标签，这样我能一眼看出哪些是外食、哪些是自己做的。
5. 作为一个记录饮食的用户，我想在卡片上直接给一笔饮食补一个「加班餐」标签，这样我不用为了加个标签重填整笔记录。
6. 作为一个记录饮食的用户，我想在卡片上删掉一个不再适用的标签，这样我的饮食分类保持干净。
7. 作为一个已经在别处用标签的用户，我想在健身/饮食里输入标签时看到跟其他模块一样的建议列表，这样我不会为同一件事造出「胸」和「胸部」两个标签。
8. 作为一个用键盘操作的用户，我想能在卡片上按回车展开标签编辑器、并在输入框里用键盘增删标签，这样我不需要鼠标。
9. 作为一个用读屏的用户，我想在标签编辑器展开时听到它是「编辑标签」，这样我知道焦点进了哪里。
10. 作为一个用读屏的用户，我想标签的增删是即时的，不需要额外确认，这样操作步骤跟其他模块一致。
11. 作为一个已经给某笔记录打了标签的用户，我想在搜索框里敲 `#标签` 依然能搜到它，这样这次改动没有破坏已有的搜索能力。
12. 作为一个用户，我想在健身与饮食页改标签，每改一次只影响那一条记录，这样我不会误改到别的流水。
13. 作为一个用户，我想标签数量有和其他模块一样的上限约束，这样我不会意外造出上百个标签的畸形数据。
14. 作为一个用户，我想标签改动后立刻写进本地存储，这样我刷新页面改动还在。
15. 作为一个用户，我想标签改动随备份一起导出、导入后还在，这样标签不会因为换设备而丢失。
16. 作为一个用户，我想在老存档上也能用这个功能，这样我不需要为了加标签而重新录入历史数据。
17. 作为一个用户，我想在「今天没有记录」的空状态下看不到多余的标签 UI，这样空页面保持干净。
18. 作为一个用户，我想在筛选/搜索出结果后，每张卡片的标签编辑器依然正常，这样混合场景下不会出问题。
19. 作为一个用户，我想标签编辑器的展开/收起不改变卡片高度到会影响阅读的程度，这样列表不会因为编辑而大幅跳动。
20. 作为一个维护者，我想这次改动不引入任何数据迁移，这样 `STORE_VERSION` 与已有存档的兼容性不受影响。
21. 作为一个维护者，我想健身与饮食两处用的是同一个已有组件、同一套调用形状，这样两处实现不会各自漂移。
22. 作为一个维护者，我想这个功能有测试守着（展开、增删、落库），这样将来重构卡片布局时不会无声破坏它。

## Implementation Decisions

**复用既有组件，不新建。**

- 卡片上的就地编辑器用已有的标签编辑组件（就是读书、游戏、任务、写作、开发项目在用的那一个）。它的接口形状为：`tags`（只读数组）、`onChange`（回调）、可选 `suggestions`、可选 `max`、可选 `className`。**不修改该组件本身。**
- 标签建议复用既有的「全站标签建议」hook，与其他模块同一个来源。
- 标签片（只读展示）与标签输入框都不新增组件。

**复用既有 store 方法，不改 store。**

- 健身与饮食两个 store 都已经暴露了 `updateRecord(id, patch)`，并且都接受 `Partial<Omit<Record,'id'>>`。写入标签就是 `updateRecord(record.id, { tags })`。
- 两个 store 的 `updateRecord` 实现已经会把改动写进持久化层。**不改它们的实现。**
- 不新增 action、不新增 selector。

**零 schema 变更。**

- 健身记录与饮食记录的类型上**已经有** `tags: string[]` 字段，且已有默认值与归一化。本次不改类型、不改备份 schema、不改归一化逻辑。
- 因此 **不 bump `STORE_VERSION`、不 bump `BACKUP_SCHEMA_VERSION`**。老存档与老备份继续可读（符合仓库「不丢数据」的硬约束）。

**交互沿用既有约定。**

- 收起态是只读标签片，展开态是输入框 + 「完成」按钮；展开态由「编辑标签」这一无障碍名标识。
- 回车与逗号都收下标签；标签上限沿用该组件的既有上限，不在页面层另设。
- 改动即时落库，没有「保存」步骤——与另外六个模块一致。

**与全局搜索的关系（重要）。**

- 全局实体索引**已经**把健身与饮食记录的 `tags` 收录进 `SearchableEntity`，因此 `#标签` 搜索今天就能命中这两类记录。**本次不碰索引逻辑**，只补页面上的展示与编辑入口。这条要在实现时验证：改完之后 `#标签` 搜索依然命中。

**与 ADR 的关系。**

- 本次不涉及网络、同步或后端，不与 ADR-0002（跨设备同步）冲突。标签随备份导出，因此也为将来同步时的按条目合并保留了一致的数据形状。

## Testing Decisions

**什么算好测试。** 只测外部行为：用户在卡片上看到什么、点了什么、之后数据变成什么。不测组件内部状态名、不测 `useState` 有没有被调用、不测 DOM 结构层级。断言点落在「记录的标签变了」和「屏幕上出现了/消失了哪些标签文字」这两个可观察事实上。

**要测的模块。**

1. **健身页**：记录卡片渲染已有标签；展开编辑器、加一个标签、断言该条记录（store 里那一条）的 `tags` 变了且**只有这一条**变了；删掉一个标签同理。
2. **饮食页**：同上。
3. **建议来源**：输入时出现的建议与别处一致（可断言建议列表来自同一个 hook，而不是各页自造）。
4. **边界**：没有标签的记录收起时是干净的空态、不渲染多余节点；达到标签上限时不能再加。
5. **回归保护**：改完标签后，全局 `#标签` 搜索仍能命中该条健身/饮食记录（守住索引与页面并存这件事）。

**既有先例（照这些写）。**

- 组件层测试的先例在 `src/components/ui/tags.test.tsx`——标签编辑器的展开/增删行为已有测试，可直接参照其断言风格。
- 页面层测试的先例在 `src/pages/DevPage.test.tsx` 与 `src/pages/JournalPage.test.tsx`：前者演示了「store 里那条记录是否真的变了」这种断言（归档用例），后者演示了页面上的标签输入如何测。
- 测试环境是 vitest + jsdom，`globals: false`（要显式 import `describe/it/expect`），setup 在 `src/test/setup.ts`，IndexedDB 有 stub（`src/test/indexedDbStub.ts`）。不需要新开测试基建。

**怎么跑。**

- `npm run test` 必须全绿（当前基线 1569 条 / 93 文件），且本次新增用例不能靠放宽既有断言来通过。
- 交付前另跑 `npm run typecheck && npm run lint && npm run format:check`。
- 真浏览器冒烟（`npm run e2e`）不进 CI，本次不强制新增 e2e 用例。

## Out of Scope

- **页内的标签筛选条**（「只看某个标签的记录」）。全局 `#标签` 搜索已经覆盖了「按标签找记录」这一需求；页内筛选条是另一件事（要扩 `useEntityList` 的筛选维度），混进来会把小改动撑成中改动。
- **给健身/饮食记录加「打开某条记录」的入口**。全局索引里这两类记录当前标着不可聚焦，点不进去；这是独立问题，与标签编辑器无关。
- **批量打标签**。已有批量标签弹窗服务于别的模块，本次不扩展到健身/饮食。
- **给标签加颜色、分组、层级、重命名**。标签仍是纯字符串数组。
- **改动标签编辑组件本身**（例如给它加新 props）。若实现时发现确实需要改，先回来说，不要顺手改。
- **任何数据迁移、`STORE_VERSION` / `BACKUP_SCHEMA_VERSION` 变更。**
- **同步相关的一切**（ADR-0002 的工作不在本 issue 范围内）。

## Further Notes

**这个 issue 的由来。** README 里那份「这一版明确没做」清单原先列了 6 项，其中 4 项经核实其实**已经实现**（开发页归档、EmptyState 示例数据、导出 PNG、自定义日期区间），是当时从 `docs/Life-Manager-V2-优化建议.md` 的过期进度行抄过来的。那份清单已在本轮更正。本次要做的是清单里**真正仍然开放**的几项之一，也是性价比最高的一项：组件、字段、store 方法全都已经就位，缺的只是两个消费方。

**为什么它便宜。** 三件事都已经存在，且都已在别处验证过：标签编辑组件（6 处消费方）、记录类型上的 `tags` 字段、两个 store 的 `updateRecord`。所以工作量集中在「把组件挂到两个页面的卡片上 + 补测试」，没有任何一处需要新造接缝。不需要迁移也就意味着**没有数据丢失风险**，符合仓库「不丢数据」的硬约束。

**词表。** 术语沿用 `CONTEXT.md`。注意「标签」在本仓库语境里指记录上的自由字符串分类，与「导航项」「条目」不是一回事；写测试名与提交信息时不要混用。
