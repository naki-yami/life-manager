# 技术方案文档

## 1. 技术选型总览

| 类别 | 选择 | 理由 |
|------|------|------|
| 前端框架 | React 18 | 生态最成熟，组件库丰富，社区支持好 |
| 开发语言 | TypeScript | 类型安全，代码可维护性强，减少运行时错误 |
| 构建工具 | Vite | 开发体验好，热更新快，构建速度快 |
| 样式方案 | Tailwind CSS | 原子化 CSS，开发效率高，易于实现简洁现代风格 |
| 数据存储 | localStorage | 浏览器原生支持，无需后端，数据持久化 |
| 路由方案 | React Router v6 | 官方推荐，API 简洁，支持嵌套路由 |
| 状态管理 | Zustand | 轻量级，API 简单，适合中小型项目 |
| 图标库 | Lucide React | 图标质量高，体积小，按需引入 |
| 日期处理 | date-fns | 轻量级，Tree-shaking 友好，API 简洁 |
| 表单处理 | React Hook Form | 性能好，API 简洁，减少不必要的重渲染 |

## 2. 为什么选择这些技术

### 2.1 React 18 vs Vue 3

**选择 React 的理由**：
- 生态更成熟，第三方库选择更多
- 社区更大，遇到问题更容易找到解决方案
- TypeScript 支持更完善
- 适合复杂的多模块应用

**Vue 3 的优势**：
- 学习曲线更平缓
- 模板语法更直观
- 对于个人项目也完全够用

**结论**：React 生态更丰富，适合长期维护和扩展。

### 2.2 为什么用 Tailwind CSS

**优势**：
- 原子化 CSS，不需要写 CSS 文件
- 开发速度快，不用纠结类名命名
- 易于实现响应式设计
- 配置文件可以自定义主题色、间距等
- 生产环境自动 Tree-shaking，体积小

**对比方案**：
- CSS Modules：需要额外写 CSS 文件，开发效率低
- Styled-components：运行时 CSS-in-JS，性能略差
- 传统 CSS：维护成本高，容易样式冲突

### 2.3 为什么用 Zustand 而不是 Redux

**Zustand 的优势**：
- API 极简，学习成本低
- 代码量少，不需要写 action、reducer
- 性能优秀，自动优化重渲染
- 支持中间件（persist、devtools 等）

**Redux 的问题**：
- 样板代码多
- 配置复杂
- 对于这个项目来说过于重量级

### 2.4 为什么用 localStorage

> **已演进（V2.1）**：这一节记录的是 V2.0 的选择。现在数据主存进 IndexedDB，
> localStorage 只留设置项与兜底链路，见 §4.1「实现现状」与文末说明。

**适用场景**：
- 数据量不大（预计 < 5MB）
- 无需跨设备同步
- 无需复杂的查询和索引

**优势**：
- 浏览器原生支持，无需额外依赖
- API 简单，读写方便
- 数据持久化，刷新不丢失

**注意事项**：
- localStorage 容量限制约 5MB
- 只能存储字符串，需要 JSON 序列化
- 同步 API，大量数据读写可能阻塞主线程
- 对于这个项目来说完全够用

**备选方案**（如果数据量增大）：
- IndexedDB：容量更大，支持异步，API 复杂
- 文件系统 API：需要用户授权，兼容性问题

## 4. 核心功能实现方案

### 4.1 数据持久化

> ⚠️ 本节保留的是最初的设计草案，示例代码与当前实现已经不同（例如 store 命名、key 命名）。
> 以「实现现状（V2.0）」小节为准。

**最初方案**：封装 localStorage，统一使用 JSON 序列化

```typescript
// utils/storage.ts
export const storage = {
  get: <T>(key: string): T | null => {
    const value = localStorage.getItem(key);
    return value ? JSON.parse(value) : null;
  },
  
  set: <T>(key: string, value: T): void => {
    localStorage.setItem(key, JSON.stringify(value));
  },
  
  remove: (key: string): void => {
    localStorage.removeItem(key);
  }
};
// 注意：这里刻意不提供 clear()。localStorage.clear() 会把同一 origin 下
// 其它项目的数据一起删掉，清空本应用数据请用 store/storage.ts 的 clearAppData()
// （它只清 lm: 前缀、且默认保留自动备份快照）。
```

**Zustand persist 中间件**：
```typescript
// store/todayPlanStore.ts
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

interface Task {
  id: string;
  title: string;
  completed: boolean;
  priority: 'high' | 'medium' | 'low';
  dueDate?: string;
}

interface TodayPlanState {
  tasks: Task[];
  addTask: (task: Omit<Task, 'id'>) => void;
  toggleTask: (id: string) => void;
  deleteTask: (id: string) => void;
}

export const useTodayPlanStore = create<TodayPlanState>()(
  persist(
    (set) => ({
      tasks: [],
      addTask: (task) => set((state) => ({
        tasks: [...state.tasks, { ...task, id: Date.now().toString() }]
      })),
      toggleTask: (id) => set((state) => ({
        tasks: state.tasks.map((task) =>
          task.id === id ? { ...task, completed: !task.completed } : task
        )
      })),
      deleteTask: (id) => set((state) => ({
        tasks: state.tasks.filter((task) => task.id !== id)
      })),
    }),
    {
      name: 'today-plan-storage',
    }
  )
);
```

#### 实现现状（V2.0）

持久化配置集中在少数几个模块里，各 store 不再各写一遍：

| 关注点 | 位置 | 说明 |
|---|---|---|
| 存储后端 | `src/store/kv.ts` | 两套后端：IndexedDB（主）/ localStorage（兜底）。`resolveStoreBackend()` 每会话只判定一次；拿不到 IndexedDB 就整条退回，行为与 V2.0 一致。主题与密度固定在 localStorage（首屏防闪烁脚本读不到 IndexedDB） |
| 写入后端 | `src/store/storage.ts` | zustand 的持久化后端 + 备份/设置页的读写入口；写失败（配额写满、隐私模式）不再把异常抛进 React，而是记录并交给 `StorageAlert` 提示用户导出备份。写失败分「写不进去」与「读出来是坏的」两种，文案不同 |
| 首启搬家 | `src/store/storage.ts` 的 `readAppValue()` | 主后端里没有这条记录时，把 localStorage 里的老数据一次性搬过去；**只写不删**，老副本留作回溯 |
| 首屏等待 | `src/store/hydrate.ts` 的 `hydrateAllStores()` | IndexedDB 的读取是异步的，渲染前先等所有 store 反序列化完（1.5s 上限），免得首屏先画一帧空数据 |
| store 配置 | `src/store/persist.ts` 的 `persistOptions()` | 统一挂 `storage` / `migrate` / `merge`，避免每个 store 各漏一处 |
| 结构归一化 | `src/store/normalize.ts` + `src/services/schemas.ts` | 复用导入备份那套 zod schema，逐条补齐字段；幂等，**每次 rehydrate 都执行** |
| 快照 | `src/services/backup.ts` | 手动快照 + 每日自动快照（`ensureDailySnapshot`），最多保留 `MAX_AUTO_BACKUPS` 份；快照跟数据走同一个后端 |
| 容量告警 | `src/store/storage.ts` 的 `measureAppStorage()` | IndexedDB 时代看 `navigator.storage.estimate()` 的 origin 配额（用掉七成告警）；退回 localStorage 时仍按 3MB |
| 删除策略 | `src/store/storage.ts` 的 `clearAppData()` | 两个后端一起清（只清一边的话老副本会「死而复生」），默认保留快照；**禁止 `localStorage.clear()`** |

两条必须遵守的规则：

1. **数组内单条记录新增字段**（例如给 Task 加一个字段）：只改 `src/services/schemas.ts` 里
   对应 schema 的默认值即可，**不要写进 `migrate`**。zustand 只在存储里的版本号与当前版本号
   不一致时才调用 `migrate`，写在那里等于只对老版本生效一次，之后就再也不会执行。
2. **store 根级结构变化**（增删整个字段、换 key 名）才需要 bump `STORE_VERSION`。

**已做（V2.1）**：数据主存进 IndexedDB，localStorage 退居「设置项 + 兜底」。

- 老数据在首启时自动搬进 IndexedDB，localStorage 里那份原样保留；
- 拿不到 IndexedDB（隐私模式、被别的标签页占着）时整条链路退回 localStorage，不会因此报错或丢数据；
- 主题与密度仍然只写 localStorage —— 首屏那段防闪烁内联脚本是同步执行的，读不到 IndexedDB。

实现与取舍见 `docs/Life-Manager-V2-优化建议.md` §9「V2.1 第八阶段：IndexedDB 存储层」。

### 4.2 主题切换

**方案**：使用 Tailwind 的 dark mode + Zustand 状态管理

```typescript
// hooks/useTheme.ts
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

interface ThemeState {
  theme: 'light' | 'dark';
  toggleTheme: () => void;
}

export const useThemeStore = create<ThemeState>()(
  persist(
    (set) => ({
      theme: 'light',
      toggleTheme: () => set((state) => ({
        theme: state.theme === 'light' ? 'dark' : 'light'
      })),
    }),
    {
      name: 'theme-storage',
    }
  )
);

// 在 App.tsx 中应用
useEffect(() => {
  document.documentElement.classList.toggle('dark', theme === 'dark');
}, [theme]);
```

### 4.4 数据导出/导入

```typescript
// utils/backup.ts
export const exportData = (): void => {
  const data = {
    todayPlan: useTodayPlanStore.getState().tasks,
    reading: useReadingStore.getState().books,
    // ... 其他模块数据
    exportedAt: new Date().toISOString(),
  };
  
  const blob = new Blob([JSON.stringify(data, null, 2)], {
    type: 'application/json'
  });
  const url = URL.createObjectURL(blob);
  const a = document.createElement('a');
  a.href = url;
  a.download = `backup-${Date.now()}.json`;
  a.click();
  URL.revokeObjectURL(url);
};

export const importData = (file: File): Promise<void> => {
  return new Promise((resolve, reject) => {
    const reader = new FileReader();
    reader.onload = (e) => {
      try {
        const data = JSON.parse(e.target?.result as string);
        // 恢复各个模块的数据
        useTodayPlanStore.setState({ tasks: data.todayPlan });
        useReadingStore.setState({ books: data.reading });
        // ... 其他模块
        resolve();
      } catch (error) {
        reject(error);
      }
    };
    reader.readAsText(file);
  });
};
```

## 5. 开发规范

### 5.1 代码规范
- 使用 ESLint + Prettier 统一代码风格
- TypeScript 严格模式（strict: true）
- 组件使用函数式组件 + Hooks
- 文件命名使用 PascalCase（组件）或 camelCase（工具函数）

### 5.2 Git 规范
- 每次改动必须提交 commit
- commit message 遵循 Conventional Commits 规范
  - `feat`: 新功能
  - `fix`: 修复 bug
  - `docs`: 文档更新
  - `style`: 代码格式调整
  - `refactor`: 重构
  - `test`: 测试相关
  - `chore`: 构建/工具链相关

### 5.3 测试规范
- 使用 Vitest 进行单元测试
- 使用 React Testing Library 测试组件
- 核心功能必须有测试覆盖
- 交付前确保所有测试通过

## 6. 性能优化

### 6.1 代码分割
- 使用 React.lazy + Suspense 懒加载页面组件
- 路由级别的代码分割，减少首屏加载时间

### 6.2 状态管理优化
- Zustand 自动优化重渲染，只订阅需要的状态
- 避免在组件中直接操作 localStorage，统一通过 store

### 6.3 样式优化
- Tailwind CSS 自动 Tree-shaking，生产环境只打包用到的样式
- 使用 CSS 变量实现主题切换，避免重复样式

## 总结

这套技术方案以 **简洁、高效、可维护** 为核心原则：

- **React + TypeScript** 保证代码质量和可维护性
- **Vite** 提供极致的开发体验
- **Tailwind CSS** 快速实现简洁现代的设计
- **localStorage + Zustand** 轻量级数据持久化方案
- **React Router** 简洁的路由管理

所有技术选型都经过充分论证，适合这个个人工作生活管理应用的需求。
